# Edy — архитектурные решения (v2.1)

Документ фиксирует решения, принятые после обсуждения концепции v2.0.
Концепция остаётся прежней, здесь только то, что уточнено или изменено.

## Рамки продукта

| Вопрос | Решение |
|---|---|
| Платформа | Только **macOS** (arm64 и amd64). WebView — WKWebView, PTY — нативный, секреты — Keychain. |
| Форма продукта | **Агентная панель** поверх проекта, а не полноценный редактор. Код пользователь правит в своём редакторе. |
| Аудитория | Личный инструмент. Без установщика, автообновлений и телеметрии. |
| Язык | Интерфейс и промпты агентов — **русский** (основной) и английский. |
| Порядок разработки (MVP) | OmniRoute (API + CLI) → один агент с хуками → Shadow Git → Оркестратор и микро-агенты → Web-адаптер. |

## Технические решения

| Тема | Решение | Почему |
|---|---|---|
| CGO | **Ядро — без CGO.** Вместо Tree-sitter: Go разбирается встроенным `go/ast`, Python — модулем `ast` самого Python. CGO нужен только окну Wails на macOS. | С CGO нельзя собрать Mac-версию ядра на сервере сборки. Для языков проекта (Go и Python) хватает родных парсеров. |
| Headless-браузер | Используем **установленный у пользователя Chrome** (через CDP). | Не тащим Chromium в бинарник. |
| Ротация ключей | Ключ переключается прозрачно, пока клиенту не ушёл первый байт. Ошибка в середине стрима — повтор запроса целиком. | Нельзя склеить один ответ из двух разных генераций. |
| Web-адаптер | Экспериментальная функция «на свой риск». | Нарушает ToS сервисов, селекторы часто ломаются. |
| Формат OmniRoute | Наружу — OpenAI `/v1/chat/completions` (SSE-стриминг, tool calling, картинки). Внутри — любой OpenAI-совместимый API или Anthropic Messages API. | Формат OpenAI понимают почти все внешние программы. |
| Доступ к прокси | Открыт для **внешних программ**, но только с Bearer-токеном. Слушаем только `127.0.0.1`. | Иначе любой локальный процесс тратил бы ваши ключи. |
| Shadow Git | Отдельный скрытый git-репозиторий в `.edy/shadow` (go-git). | Дедупликация, диффы, squash в один коммит. |
| Ручные правки во время работы агента | Файлы, с которыми работает агент, **блокируются**. | Агент не перезапишет ваши правки. |
| Эмбеддинги | Локально через Ollama или через API. Векторы хранятся в чистом Go (`chromem-go`). | Без лишнего CGO. |
| Хуки | Запускаются прямо на машине пользователя. | Песочница пока не нужна. Агент работает только внутри папки проекта. |
| UI-бот | Меняет только безопасный набор настроек (тема, шрифт, раскладка) в JSON. CSS/JS интерфейса не трогает. | Нельзя «сломать» IDE. |
| Бюджет | Дневной лимит в долларах, учёт токенов и стоимости по каждому агенту (заголовок `X-Edy-Client`). | Контроль расходов. |

## Решения по основному функционалу (этапы 2–3)

| Вопрос | Решение |
|---|---|
| Языки проектов | **Go и Python**: хуки `go vet`/`go test` и `ruff`/`pytest`, грамматики Tree-sitter для Go и Python. |
| Куда идёт результат | После Approve — один коммит в **новую ветку** `edy/<задача>`. Текущая ветка не трогается. |
| Как ставятся задачи | В **чате** интерфейса: обсуждаем задачу с Оркестратором, утверждаем план, после этого начинается работа. |
| Инструменты для CLI | 1) **Эмуляция tools в OmniRoute**: для CLI-провайдеров описание инструментов вставляется в промпт, а ответ разбирается в `tool_calls` формата OpenAI. Так любой CLI работает агентом Edy под контролем хуков и Shadow Git. 2) **MCP-сервер Edy** (`edy mcp`): Claude Code, Antigravity, Codex, Gemini CLI и Cursor подключают его и получают инструменты Edy (скелет проекта, тесты, чекпоинты). |
| Skills | Наборы инструкций (`<имя>/SKILL.md`, формат Claude Code) в `skills/` папки данных Edy и в `.edy/skills/` проекта. Агент Edy видит их список и грузит нужный через `use_skill`; внешние агенты получают их по MCP. |

## Этап 2–3. Агентный цикл — что уже сделано

```
internal/omniroute/toolemu.go  эмуляция tools для CLI-утилит и веб-чатов
internal/agent/
  llm.go        клиент OmniRoute (формат OpenAI)
  workspace.go  инструменты агента, только внутри папки проекта
  hooks.go      хуки: go vet/go test, ruff/pytest или свои в .edy/hooks.json
  shadow.go     Shadow Git: скрытый репозиторий .edy/shadow.git со снимками
  task.go       цикл задачи, Circuit Breaker, Approve/Reject
```

**Эмуляция tools.** Если у CLI- или веб-провайдера в запросе есть `tools`, OmniRoute добавляет в промпт
описание инструментов и протокол `<tool_call>{"name": …, "arguments": …}</tool_call>`. Прошлые вызовы и
результаты он переводит в текст, а ответ модели разбирает обратно в `tool_calls` формата OpenAI.
Для агента `agy` выглядит как обычный API с tools.

**Цикл задачи** (`edy task -model слабая,сильная "задача"`):
1. Проект должен быть git-репозиторием без незакоммиченных изменений. `.edy/` прячется от основного git
   через `.git/info/exclude`.
2. Снимок №0 в Shadow Git — исходное состояние.
3. Модель работает инструментами: `list_files`, `read_file`, `write_file`, `replace_in_file`, `delete_file`,
   `finish`. После каждой правки делается снимок.
4. После `finish` запускаются хуки. Если они упали, их вывод уходит модели с пометкой «Исправляй».
5. **Circuit Breaker:** после 3 провалов подряд проект откатывается к снимку №0, и задача переходит
   к следующей модели в цепочке, которая начинает с чистого листа. Если моделей не осталось, статус
   «нужна помощь человека», проект в исходном состоянии.
6. **Approve:** создаётся ветка `edy/<задача>-<дата>` с одним коммитом, проект переключается на неё,
   `main` не трогается. **Reject:** откат к снимку №0.

Агент не выходит за папку проекта: абсолютные пути, `..`, `.git`, `.edy` и символические ссылки наружу
запрещены. Команд оболочки у агента нет, проверки запускает сам Edy.

### Оркестратор и проекты в интерфейсе

```
internal/orchestrator/  Оркестратор: видит структуру проекта, уточняет задачу, выдаёт план в <plan>…</plan>
internal/tasks/         фоновые задачи агента: лента событий, Approve/Reject/остановка, одна задача на проект
internal/api/projects.go  API проектов, снимков, Оркестратора и задач
```

- **Чат → «Оркестратор»:** выбираются проект, модель Оркестратора, исполнитель и резервная модель
  для Circuit Breaker. Оркестратор кода не пишет: обсуждает задачу и предлагает план.
  Под планом кнопка «▶ Начать работу».
- **Ход работы** виден в чате вживую: инструменты, снимки, проверки, Circuit Breaker. Есть кнопка «Остановить»:
  остановленная задача откатывается целиком.
- **Решение:** итог, список изменённых файлов и кнопки «Approve — в новую ветку» и «Reject — откатить».
- **Раздел «Проект»:** список папок, статус («готов», «идёт задача», «ждёт решения» или почему не готов), текущая ветка,
  снимки Shadow Git и «Откатить сюда» к любому снимку.
- Задачи хранятся в памяти процесса: после перезапуска `edy ui` лента пропадает, а снимки в `.edy/shadow.git` остаются.

### Вкладка «Git» (`internal/gitops`, `internal/api/gitapi.go`)

- **Источники проекта:** обычная папка без git (снимки в Shadow Git, результат остаётся в папке),
  локальный git-репозиторий, клон с GitHub, GitLab или Gitea (`file://` тоже поддерживается).
  Клоны лежат в `repos/` в папке данных Edy.
- **Аккаунты:** GitHub, GitLab (gitlab.com или свой сервер), Gitea (свой сервер). Токены хранятся в SQLite
  зашифрованными (AES-GCM). Git получает токен заголовком `http.extraHeader` только на время команды,
  в URL и `.git/config` он не записывается.
- **Как оформлять результат агента** (настройки проекта):
  - коммит: новая ветка `edy/…`, прямо в текущую ветку или без коммита;
  - после коммита: ничего, push или push с Pull Request (GitHub, Gitea) либо Merge Request (GitLab);
  - свой автор коммитов (`--author`) и префикс сообщения.
- **Работа с репозиторием напрямую:** ветка, origin, незакоммиченные файлы, последние коммиты, Pull (только fast-forward) и Push.

### Журнал агентов (таблицы `agents` и `agent_events` в SQLite)

- **Кто записывается:** каждый агент. Оркестратор — один агент на разговор, исполнитель — по одному
  на каждую модель, взявшую задачу. Если сработал Circuit Breaker, в журнале будет два исполнителя.
- **Что хранится:** роль, модель, проект, задача, время создания и окончания, состояние (работает, закончил,
  не справился, остановлен, прерван), итог или ошибка и все действия по порядку.
- **Перезапуск:** при старте `edy serve` или `edy ui` агенты, оставшиеся «работающими», помечаются «прерван».
- **Окно «Агенты»:** список со статусами, обновляется вживую. По щелчку — карточка агента и полный журнал действий.

### MCP-сервер и скиллы (`internal/mcp`, `internal/skills`, `internal/api/mcpapi.go`)

**Зачем:** Claude Code, Gemini CLI, Cursor и другие MCP-клиенты работают с проектом инструментами Edy —
с теми же ограничениями, что и агент Edy.

**Инструменты:** `project_skeleton`, `search_code`, `list_files`, `read_file`, `write_file`, `replace_in_file`,
`delete_file` (только внутри проекта, без `.git` и `.edy`), `run_checks` (хуки проекта), `list_skills`, `use_skill`.
Скиллы доступны и как MCP prompts.

**Контроль:**
- каждая правка сохраняется снимком в Shadow Git (`MCP: replace_in_file calc.go`), откат — в разделе «Проект»;
- пока над проектом идёт задача Edy, правки через MCP запрещены (чтение разрешено);
- каждое подключение — запись в окне «Агенты» (роль «Внешний агент (MCP)», имя клиента, журнал вызовов).

**Транспорты:**
- **HTTP** — `POST /mcp?project=<путь>` на адресе OmniRoute, с токеном Edy (Streamable HTTP, ответы JSON,
  сессии через `Mcp-Session-Id`). Проект должен быть добавлен в Edy.
- **stdio** — `edy mcp -project <папка>`. Если Edy запущен, команда пересылает запросы в него (журнал и
  блокировки работают) и сама добавляет папку в проекты; если нет — обслуживает проект сама.

Готовые команды для Claude Code и JSON для Gemini CLI и Cursor — на экране «Подключение».

**Оркестратор сам даёт MCP исполнителю.** Если задача досталась CLI-утилите, которая умеет брать MCP-сервер
из аргументов (сейчас это Claude Code), Edy запускает её в папке проекта с MCP Edy вместо пошаговой эмуляции:
- адрес `/mcp` с одноразовой привязкой к задаче (`bind=…`): правки через него не блокируются этой же задачей,
  вызовы и снимки идут в ленту задачи, а остальные MCP-клиенты в это время только читают;
- конфиг с токеном — временный файл с правами 0600, удаляется сразу после запуска; токен отдаётся только
  на `/mcp` этой машины;
- `--strict-mcp-config`, разрешены инструменты `mcp__edy`, свои `Edit`, `Write`, `MultiEdit`, `NotebookEdit`
  и `Bash` у Claude Code отключены — все правки идут через Edy;
- после ответа утилиты Edy сам запускает проверки; если они упали, утилита получает отчёт и правит дальше
  (до 3 раз), потом срабатывает Circuit Breaker.

**Внешние MCP-серверы выбирает Оркестратор.** В разделе «MCP-серверы» хранится каталог: имя, описание «для чего»,
HTTP-адрес с заголовками или команда stdio с аргументами и переменными окружения (настройки зашифрованы, в
интерфейс значения заголовков и переменных не отдаются). Есть шаблоны: Playwright, Context7, Fetch, GitHub.
- Включённые серверы с описаниями попадают в инструкции Оркестратора. Он выдаёт нужные строкой `MCP: имя1, имя2`
  в плане; в карточке плана они видны отдельно.
- При «Начать работу» список берётся из утверждённого плана и сверяется с каталогом: выдуманный или выключенный
  сервер не выдаётся.
- Исполнитель с MCP получает их в конфиге вместе с `edy` и разрешение на их инструменты; в OmniRoute
  передаются только имена (`X-Edy-MCP-Servers`), настройки берутся из каталога. Исполнитель без MCP получает
  предупреждение в ленте задачи.

Остальные CLI (Antigravity, Codex, Gemini CLI…) и веб-чаты работают через эмуляцию инструментов в промпте.
В списке «Исполнитель» модели с MCP помечены «· MCP».

**Скиллы:** формат Claude Code — папка `<имя>/SKILL.md` с заголовком `name`/`description` (или файл `<имя>.md`).
Общие лежат в `skills/` папки данных Edy, скиллы проекта — в `.edy/skills/`; при совпадении имён побеждает скилл
проекта. Создаются и удаляются в разделе «Проект». Агент Edy получает список скиллов в системном промпте и
загружает нужный через `use_skill` — это работает с любым провайдером, включая CLI и веб-чаты.

### Context Engine (`internal/codeindex`)

- **Скелет проекта:** файлы, типы с полями, интерфейсы с методами, функции и методы с сигнатурами
  и номерами строк, классы и функции Python. Тел функций в скелете нет.
  - **Go** разбирается встроенным `go/ast`.
  - **Python** — модулем `ast` через `python3 -I` (скрипт `pyskeleton.py` встроен в бинарник).
    Если `python3` нет, объявления `def`/`class` ищутся по строкам.
  - **Остальные текстовые файлы** (md, js/ts, yaml, sql…) попадают в список и в поиск.
- **Поиск кода:** BM25 по кускам кода. Для Go и Python кусок — это объявление, для остального — блок по 60 строк.
  Идентификаторы разбиваются на слова: `parseHTTPRequest` → parse, http, request; `user_name` → user, name.
- **Кто пользуется:**
  - агент — инструменты `project_skeleton` и `search_code`, с них он начинает работу;
  - Оркестратор — получает скелет вместо списка файлов;
  - пользователь — раздел «Проект» → «Карта проекта».
- **Дальше:** векторный поиск через эмбеддинги локальной Ollama.

### Окно Wails (`cmd/edy-app`, `internal/app`)

- **Общий запуск.** `internal/app` поднимает Edy целиком: OmniRoute, API, интерфейс, браузеры, задачи и журнал.
  Им пользуются и `edy serve`/`edy ui`, и окно.
- **Что показывает окно.** Wails открывает маленькую стартовую страницу, и она сразу переходит на
  `http://127.0.0.1:11435/#token=…&app=1`. Поэтому в окне работает ровно тот же интерфейс, что в браузере,
  включая потоковые ответы.
  - Если Edy уже запущен (`edy serve`), окно подключается к нему.
  - Если запуск не удался, окно показывает ошибку.
- **Ссылки.** Внешние ссылки в окне открываются в браузере по умолчанию через `POST /api/open` (только http/https).
- **Один экземпляр.** Повторный запуск приложения показывает уже открытое окно.
- **Сборка — только на Mac**, нужны Go и Xcode Command Line Tools: `scripts/build-macos-app.sh` → `build/Edy.app`.
  - Команда `edy` кладётся в `Contents/Resources/bin/edy`, а не рядом с окном: файловая система Mac
    не различает регистр, и `edy` перезаписал бы `Edy`.
  - В `Info.plist` разрешена локальная сеть (`NSAllowsLocalNetworking`).
  - Приложение подписывается ad-hoc.
- **Без тега `desktop`** `cmd/edy-app` собирается заглушкой, поэтому `go build ./...` и `go test ./...` работают без CGO.

## Этап 1. OmniRoute — что уже сделано

```
cmd/edy/              CLI: serve, token, provider, key, budget, spend
internal/vault/       AES-256-GCM, мастер-ключ в macOS Keychain
internal/store/       SQLite (modernc.org/sqlite, без CGO): провайдеры, ключи, настройки, расходы
internal/omniroute/
  server.go           HTTP-сервер, авторизация, маршрутизация, ротация ключей, бюджет
  openai.go           адаптер для любых OpenAI-совместимых API
  anthropic.go        адаптер Anthropic: перевод формата запросов и SSE-событий
  cli.go              CLI-адаптер: утилита в PTY, готовые профили ollama / claude-code / aider
  sanitize.go         очистка потока терминала от ANSI, спиннеров и прогресс-баров
```

### Как идёт запрос

1. Клиент (агент Edy или внешняя программа) шлёт `POST /v1/chat/completions`
   с `model: "<провайдер>/<модель>"`, например `anthropic/claude-opus-5-5`.
2. Сервер проверяет токен и дневной бюджет, находит провайдера в базе.
3. Ключи провайдера перебираются по порядку:
   - **429** — ключ уходит на перерыв (по `Retry-After`, иначе на 60 с), запрос идёт со следующим ключом;
   - **401/403** — ключ отключается навсегда;
   - другие ошибки возвращаются клиенту.
4. Адаптер всегда работает потоком. Если клиент не просил `stream`, роутер сам собирает
   ответ в единый `chat.completion`.
5. Токены и стоимость записываются в таблицу `usage`.

### Известные ограничения адаптера Anthropic

- Блоки thinking не передаются в формате OpenAI. В многошаговых циклах с инструментами
  предыдущее «мышление» модели не возвращается обратно в API.
- `temperature`/`top_p` отбрасываются: новые модели Claude отвечают на них ошибкой 400.
- Если клиент не передал `max_tokens`, используется 32 000.

### CLI-адаптер

- На каждый запрос запускается отдельный процесс в PTY (`creack/pty`, без CGO) с окном 500×50,
  чтобы было меньше переносов строк. Команда задаётся массивом аргументов с подстановками
  `{model}` и `{prompt}`. Готовые профили: `ollama`, `claude-code`, `aider`, `antigravity` (CLI `agy`).
- Если в запросе одна реплика пользователя, она передаётся как есть. Иначе диалог сворачивается
  в один текст с разделами «Инструкции / Пользователь / Ассистент».
- Очистка работает построчно: строка уходит клиенту, когда завершена переводом строки, потому что
  одиночный `\r` перезаписывает её с начала. Поэтому текст приходит строками, а не по токенам.
- Рабочая папка утилиты задаётся заголовком `X-Edy-Workdir`. Это важно для Aider и Claude Code,
  которые сами правят файлы.
- Если клиент отключился, убивается вся группа процессов утилиты.
- Картинки и tools не поддерживаются (ответ 400). Токены оцениваются грубо: символы / 4.

### Веб-интерфейс

- `internal/ui` — одна страница (HTML/JS без сборки), встроенная в бинарник через `embed`.
  Её же позже покажет окно Wails.
- `internal/api` — JSON API для интерфейса на том же порту. Каждый запрос требует Bearer-токен
  OmniRoute, поэтому чужой сайт в браузере не может управлять Edy через localhost.
  Секреты ключей API не отдаёт никогда.
- Токен передаётся интерфейсу в `#`-части адреса: браузер не шлёт её на сервер и не пишет в логи.
- Через API можно запускать установщики только из встроенных профилей, а не произвольные команды.

### Web-адаптер (`internal/webchat`, `omniroute/web.go`)

**Два вида браузера:** выбираются для каждого веб-подключения.

| | Изолированный Chromium | Мой Google Chrome |
|---|---|---|
| Что это | Обычный Chromium (официальные сборки проекта Chromium), который Edy скачивает в свою папку (`edy web chromium`) | Установленный Google Chrome |
| Профиль | Своя папка `web-profiles/<провайдер>` | Тоже своя папка Edy: обычные вкладки и аккаунты пользователя не затрагиваются |
| Когда выбирать | По умолчанию: полностью отдельное окружение | Если сайт не пускает в Chromium |

**Окружения:** у каждого веб-провайдера своя папка профиля, свой процесс браузера, своя пауза и свой дневной лимит.
Можно подключить несколько аккаунтов одного сайта под разными именами. При удалении провайдера его окружение
(cookies, вход) удаляется.

**Вход в два этапа:**
1. «Войти» открывает сайт в **обычном окне браузера без подключения автоматизации**. Пользователь входит и закрывает окно.
2. Когда окно закрыто, Edy сам запускает тот же профиль под управлением и **проверяет подключение**:
   открывается ли сайт и есть ли поле ввода. Статус показывается в интерфейсе: «не проверено», «открыто окно входа»,
   «проверяю…», «работает», «нужно войти», «ошибка». Есть и кнопка «Проверить».

**Сторож:** перед каждым запросом Edy проверяет, что браузер жив. Если нет — перезапускает его вместе
со всеми процессами. Закрытую вкладку открывает заново. Если поле ввода не появилось, статус становится
«нужно войти», а снимок страницы сохраняется в `web-debug/`.

**Как снижается риск блокировки:** Edy ведёт себя как обычный пользователь, а не маскируется. Вход вручную
в обычном окне, видимый браузер, один запрос за раз, пауза между запросами (15 с) и дневной лимит (150).
Подмены отпечатков, stealth-патчей и обхода капчи нет и не будет. Автоматизация всё равно нарушает
правила сервисов.

**Одна вкладка:** Chrome при запуске сам открывает пустую вкладку. Edy подключается именно к ней, а не создаёт
новые, поэтому лишних вкладок `about:blank` нет.

**Отправка:** вставка текста (`Input.insertText`, запасной путь — `execCommand`), затем Enter. Если через
1,2 с текст всё ещё в поле, ответ не начался и сообщений не прибавилось, Edy нажимает кнопку отправки:
сначала по селекторам сайта, затем по общим признакам (`data-testid`/`aria-label` с «send»/«отправ»,
`type=submit`). Каждый селектор — список вариантов через запятую.

**Диагностика:** при любом сбое (поле не найдено, текст не отправился, ответ не найден за 90 с) в
`web-debug/` сохраняются скриншот `.jpg` и `.json` со списком полей ввода, кнопок и крупных текстовых
блоков страницы. По нему селекторы правятся в `web-sites.json`.

**Сайты:** ChatGPT, Claude.ai, Gemini. Селекторы **на реальных аккаунтах не проверены**. Их можно поправить
в `web-sites.json` в папке данных без пересборки. Пока только текст, без картинок.

**Ограничения:** сборки Chromium промежуточные (snapshot) и обновляются повторным скачиванием. Встроенная
синхронизация «Войти в Chromium» не работает, но вход на сами сайты работает. Гарантировать, что Google
не попросит дополнительную проверку, нельзя.
