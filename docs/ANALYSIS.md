# Анализ проекта Edy

## Что это за проект

Edy — локальная агентная ИИ-панель на Go для работы с кодовыми проектами.  
Продукт запускает единый процесс с:
- OpenAI-совместимым прокси (OmniRoute),
- HTTP API для интерфейса,
- менеджером агентных задач,
- MCP-доступом для внешних агентов,
- хранением данных и секретов в локальной SQLite + Keychain.

## Ключевые модули

- `cmd/edy` — CLI-вход: запуск сервера/UI, управление провайдерами и ключами, запуск задач и MCP.
- `cmd/edy-app` — desktop-оболочка (Wails) над тем же локальным сервером.
- `internal/app` — композиция всех подсистем в один runtime (router + api + tasks + semantic + review + webchat).
- `internal/omniroute` — единая точка вызова моделей и адаптеров (`openai`, `anthropic`, `cli`, `web`), бюджет и учёт.
- `internal/tasks`, `internal/agent`, `internal/orchestrator` — постановка, планирование и выполнение задач агентами.
- `internal/mcp`, `internal/api/mcpapi.go` — MCP-транспорт и инструменты для внешних клиентов.
- `internal/store`, `internal/vault` — постоянные данные, настройки и шифрование секретов.

## Как работает система (упрощённо)

1. Пользователь запускает `edy ui` или `edy serve`.
2. `internal/app.Start(...)` поднимает HTTP-сервер, OmniRoute, API, менеджер задач и интеграции.
3. Интерфейс общается через `/api/...`, внешние клиенты через `/v1/...`, MCP-клиенты через `/mcp`.
4. Для агентных задач оркестратор формирует план, исполнитель делает изменения, проверки идут хуками, итог проходит ревью и подтверждение.
5. Для внешних инструментов Edy выдаёт MCP-инструменты с ограничениями на работу внутри проекта.

## Сильные стороны архитектуры

- Чёткое разделение подсистем (`omniroute`, `tasks`, `agent`, `api`, `store`).
- Единый runtime для CLI, browser UI и desktop UI — меньше расхождений в поведении.
- Локальная модель безопасности: токен, хранение секретов в зашифрованном виде, ограничение операций рамками проекта.
- Хорошее покрытие тестами по модулям (`*_test.go` почти в каждом пакете).
- Развитая документация в `docs/dev/*` для глубокого сопровождения.

## Зоны внимания

- Проект крупный по количеству подсистем, поэтому важна дисциплина по границам ответственности.
- Основная документация распределена по многим большим файлам — новым участникам нужен быстрый обзорный вход.
- Важна синхронизация пользовательской (`README.md`) и инженерной (`docs/dev/*`) документации, чтобы не расходились команды и сценарии.

## Рекомендации по дальнейшему развитию документации

- Поддерживать этот файл как короткую «карту проекта» для быстрого онбординга.
- При изменениях runtime-цепочки обновлять одновременно:
  - `README.md` (что и как запускать),
  - `docs/ANALYSIS.md` (архитектурный обзор),
  - профильный файл в `docs/dev/*` (детали реализации).
- Для крупных изменений фиксировать отдельно: что поменялось в потоках данных, безопасности и эксплуатационных сценариях.
