# Edy — документация для разработчика (начните отсюда)

Этот набор документов написан для разработчика, который продолжит работу над Edy. Его цель —
чтобы, прочитав его вместе с кодом, вы понимали **что** уже сделано, **как** оно устроено,
**почему** решения приняты именно так, и **что делать дальше**, не повторяя уже исправленных ошибок.

Состояние описано на коммит `b88fcbf` («Поиск по смыслу…»), ветка `claude/elegant-edison-gu1b8f`.

## 1. Что такое Edy

Edy — личная **агентная ИИ-панель для macOS**, написанная на Go. Это не редактор кода: пользователь
правит код в своём редакторе, а Edy ставит задачи ИИ-агентам и контролирует их работу над папкой проекта.

Главные части:

| Часть | Что делает | Документ |
|---|---|---|
| **OmniRoute** | Локальный прокси в формате OpenAI на `127.0.0.1:11435`. Даёт одинаковый доступ к OpenAI-совместимым API, Anthropic, терминальным утилитам (Claude Code, Ollama, Aider, Antigravity…) через PTY и к веб-чатам (ChatGPT, Claude.ai, Gemini) через браузер. Ротация ключей, дневной бюджет, учёт расходов по агентам, эмуляция tools, эмбеддинги. | [01-omniroute.md](01-omniroute.md) |
| **Агент** | Цикл «модель → инструменты → снимок → проверки»: инструменты работы с файлами только внутри проекта, хуки (go vet/test, ruff/pytest), Shadow Git (снимки каждого шага), Circuit Breaker (после 3 провалов — откат и следующая модель). | [02-agent.md](02-agent.md) |
| **Context Engine** | Скелет проекта (go/ast, Python ast), поиск кода BM25, поиск по смыслу (эмбеддинги + RRF), память проекта, скиллы. | [02-agent.md](02-agent.md) |

Объём: около 20 тыс. строк Go (из них примерно треть — тесты) и около 3,3 тыс. строк в `index.html`.

### Как это работает вместе (один процесс)

```
                         ┌───────────────────────────── процесс edy ui / Edy.app ─────────────────────────────┐
 Браузер / окно Wails ──▶│ HTTP 127.0.0.1:11435                                                               │
  (index.html)           │   /            → интерфейс (internal/ui)                                           │
                         │   /api/...     → internal/api (Bearer-токен)                                       │
 Внешние программы ─────▶│   /v1/..., /healthz → internal/omniroute (Bearer-токен) ▶ OpenAI-совм. API, Anthropic, │
 (Cursor, curl…)         │                                                        CLI в PTY, веб-чаты (CDP)  │
 Claude Code (MCP) ─────▶│   /mcp?project → internal/mcp через internal/api/mcpapi.go                          │
                         │                                                                                   │
                         │ Фон: tasks.Manager (очередь задач по проектам, эпики)                             │
                         │        └─ agent.Task ──(in-process HTTP, X-Edy-Client: agent)──▶ OmniRoute         │
                         │      review.Reviewer (X-Edy-Client: reviewer), Оркестратор (orchestrator),        │
                         │      semantic.Engine (embeddings)                                                 │
                         │ SQLite edy.db (секреты зашифрованы vault, ключ в Keychain)                        │
                         └───────────────────────────────────────────────────────────────────────────────────┘
```

Внутренние клиенты (Оркестратор, агенты, ревьюер, эмбеддинги) обращаются к OmniRoute **внутри процесса**
через `agent.InProcess(router)` — без сети, но тем же HTTP-кодом. Поэтому учёт расходов и бюджет
одинаковы для внешних и внутренних вызовов. Точный адрес и порт сверяйте в 08-app-build.md.

## 3. Путь задачи — коротко

1. Пользователь пишет в режиме «Оркестратор». Оркестратор получает контекст: исполнителей и их теги
   возможностей, статистику моделей, скиллы, каталог MCP, память, git-состояние, команду. В ответе он даёт
   план и строки `MCP:`, `Скиллы:`, `Агент:`, иногда `<subtasks>[…]</subtasks>` (эпик) или `<new_mcp>`.
2. Пользователь утверждает план. На доске проекта появляется задача: `backlog` → `queued` → `running`.
   В одном проекте одновременно выполняется одна задача (эпик — несколько подзадач в worktree).
3. Перед стартом обновляется индекс поиска по смыслу. Исполнитель (`agent.Task`) работает инструментами
   или через MCP Edy (если это Claude Code). Каждая правка — снимок в `.edy/shadow.git`.
4. После `finish` — хуки. Если провал, модель исправляет. После 3 провалов — откат и следующая модель.
5. Готово → ревьюер → `done` (или `needs_human`). Если включено автопринятие и всё прошло, задача
   принимается сама.
6. Approve → коммит в новую ветку `edy/…` (или прямо в ветку, или без коммита), при настройке push и PR.
   Reject → откат к снимку №0. Итог и уроки попадают в память проекта. Уведомление macOS.

Подробно — в [03-orchestrator-board.md](03-orchestrator-board.md).

## 4. Глоссарий

| Термин | Значение |
|---|---|
| **Провайдер** | Источник моделей. Виды (`kind`): `openai` (любой OpenAI-совместимый API, в том числе Ollama, OpenRouter), `anthropic`, `cli` (терминальная утилита в PTY), `web` (веб-чат в браузере). Модель адресуется как `провайдер/модель`. |
| **Пресет** | Готовая заготовка провайдера из каталога (`omniroute/presets.go`). |
| **Теги возможностей (caps)** | Что умеет модель: картинки, MCP, звук и т. п. (`omniroute/caps.go`). Оркестратор учитывает их при выдаче MCP и скиллов. |
| **X-Edy-Client** | Заголовок с подписью вызывающего (`orchestrator`, `agent`, `reviewer`, `embeddings`, внешний клиент). По нему считаются расходы. |
| **Эмуляция tools** | Для CLI и веб-чатов, у которых нет вызова функций: описание инструментов вставляется в промпт, ответ `<tool_call>…</tool_call>` разбирается в `tool_calls`. |
| **Задача (task)** | Единица работы агента над проектом. Хранится на доске (`board_tasks`). |
| **Эпик** | Задача, разбитая Оркестратором на подзадачи. Подзадачи идут параллельно в git worktree `.edy/worktrees/<эпик>` и сливаются в ветку `edy/epic-<id>`. |
| **Исполнитель** | Модель, которая выполняет задачу. Цепочка моделей: при провале задача переходит к следующей. |
| **Постоянный агент / команда** | Именованный агент проекта с ролью, зоной ответственности, моделью и личной памятью (`team`). |
| **Shadow Git** | Скрытый git-репозиторий `.edy/shadow.git` со снимками после каждого шага. Основной `.git` не трогается до Approve. |
| **Baseline / снимок №0** | Состояние проекта до начала задачи; к нему откатываются при Reject и отмене. |
| **Хуки** | Проверки после `finish`: `go vet`/`go test`, `ruff`/`pytest` или свои в `.edy/hooks.json`. |
| **Circuit Breaker** | После N провалов хуков подряд (по умолчанию 3) — откат и передача следующей модели. |
| **Approve / Reject** | Решение пользователя (или автопринятия) по готовой задаче. |
| **Ревьюер** | Отдельная модель, которая смотрит дифф перед Approve. |
| **Память проекта** | Короткие заметки (до 400 символов): факты, уроки, итоги задач. В промпт попадают только закреплённые и похожие на задачу; остальное агент ищет инструментом `project_memory`. |
| **Скилл** | Инструкция `<имя>/SKILL.md` (формат Claude Code) в `skills/` папки данных или `.edy/skills/` проекта. Агент грузит её через `use_skill`. |
| **MCP Edy** | MCP-сервер с инструментами Edy. Внешний агент через него правит проект под контролем Edy. |
| **Каталог MCP** | Внешние MCP-серверы, которые пользователь добавил в Edy, например с приватными ключами. |
| **Поиск по смыслу** | Эмбеддинги кусков кода и заметок + гибрид с BM25 через reciprocal rank fusion. |
| **Папка данных** | `~/Library/Application Support/Edy` на macOS: `edy.db`, `router.token`, `skills/`, `attachments/`, профили браузера и т. д. |

## 5. Быстрый старт разработчика

```sh
# Требуется Go 1.26 (см. go.mod). CGO не нужен (кроме окна Wails).
go build ./...
go vet ./...
gofmt -l .                       # должно быть пусто
go test ./...                    # все тесты; живые сервисы не нужны
go test -race ./internal/tasks   # доска и эпики — с проверкой гонок

# Запуск интерфейса в браузере (на Linux мастер-ключ Keychain может быть недоступен — см. 08-app-build.md)
go run ./cmd/edy ui

# Сборка для Mac с любой машины
CGO_ENABLED=0 GOOS=darwin GOARCH=amd64 go build -o edy-amd64 ./cmd/edy
CGO_ENABLED=0 GOOS=darwin GOARCH=arm64 go build -o edy-arm64 ./cmd/edy

# Окно Edy.app — только на Mac (нужны Xcode CLT и CGO)
scripts/build-macos-app.sh
```

Сборки, которые отдавались владельцу, назывались `edy-vNN` (последняя — `edy-v23`, darwin/amd64). Они
передавались файлом, GitHub Releases не используется.

### Как проверялся интерфейс

Автотестов UI нет. Каждое изменение интерфейса проверялось так:
1. Временный `cmd/devui/main.go`. Он открывает базу во временной папке, добавляет фейковых провайдеров
   (httptest-серверы, например заглушку эмбеддингов или демо-модель с SSE), задаёт `router_token` и
   вызывает `app.Start(st, home, "127.0.0.1:18080", nil)`.
2. Скрипт Playwright на Node (`require(… npm root -g …/playwright)`) открывает
   `http://127.0.0.1:18080/#token=…`, кликает сценарий, снимает скриншоты в светлой и тёмной теме и
   собирает ошибки консоли.
3. **`cmd/devui` удаляется перед каждым коммитом.** Подробно — в [07-ui.md](07-ui.md).

## 6. Правила работы, которые установил владелец проекта

Это требования владельца. Они действовали всё время разработки, их нужно соблюдать и дальше.

1. **Общение с владельцем — по-русски.** Интерфейс, сообщения об ошибках, комментарии в коде и промпты
   агентов тоже на русском.
2. **Ничего не пушить без явного разрешения.** Коммиты делаются локально. Push — только когда владелец
   напишет «пуш». Если хук напоминает о незапушенных коммитах, нужно ответить, что push ждёт команды «пуш».
3. **Pull request не создавать**, пока не попросят. Ветка разработки — `claude/elegant-edison-gu1b8f`.
4. **Коммиты без секретов.** Перед каждым коммитом и push проверяйте индекс и историю:
   ```sh
   git add -A
   git diff --cached | grep -nE 'sk-ant|sk-proj|sk-or-|edy-[0-9a-f]{48}|AKIA|PRIVATE KEY|ghp_|github_pat_|glpat-|AIza|xox'
   git diff --cached --name-only | grep -E '\.(db|token|pem|env)$|web-profiles|web-debug|shadow\.git|/repos/|^build/|cmd/devui'
   # перед push — то же по истории:
   git log -p origin/claude/elegant-edison-gu1b8f..HEAD | grep -nE '…тот же шаблон…'
   ```
   Обе проверки должны ничего не найти. Почтовый адрес владельца нельзя нигде использовать и никуда отправлять.
5. **Без подмены отпечатков браузера, stealth-плагинов и обхода капчи** в веб-адаптере. Это решение
   принципиальное: веб-чаты — экспериментальная функция «на свой риск», с видимым браузером,
   паузами и дневным лимитом.
6. **В коммитах не указывать идентификаторы моделей.** Сообщения коммитов — по-русски: заголовок и список
   изменений.
7. **Работать по плану сверху вниз.** Каждый пункт — отдельный коммит, проверенный тестами (и скриншотами,
   если менялся интерфейс). После пункта — сборка для Mac и короткий отчёт владельцу.

## 7. Соглашения в коде

- **Без CGO в ядре.** SQLite — `modernc.org/sqlite`, Go разбирается `go/ast`, Python — модулем `ast`
  системного `python3` (скрипт встроен). CGO нужен только `cmd/edy-app` (Wails).
- **Минимум зависимостей.** Прямые зависимости: anthropic-sdk-go, chromedp/cdproto, creack/pty, wails,
  go-keyring, modernc sqlite. Новую зависимость добавляйте, только если без неё никак.
- **Комментарии и ошибки — по-русски,** короткие и по делу. Плотность комментариев как в соседнем коде.
  У каждого пакета есть doc-комментарий, который объясняет его назначение.
- **Интерфейс — один файл** `internal/ui/static/index.html`, ванильный JS без сборки и внешних скриптов.
  Цвета — CSS-переменные, обе темы. Свои выпадающие списки вместо нативных. CSP запрещает внешние
  источники; картинки и звук разрешены только из `data:` и `blob:`.
- **Тесты рядом с кодом,** без живых сервисов: фейковые LLM (`agent.LLM`), httptest-серверы, временные
  git-репозитории (`gitProject(t)` в тестах API).
- **Опциональные зависимости — через nil-поля.** Например, `Manager.Review == nil` значит «без ревью»,
  `Workspace.Code == nil` — «поиск только по словам». Новые возможности подключайте так же, чтобы
  старые тесты не ломались.
- **Длительные git-операции не отменяются посередине:** `context.WithoutCancel` + таймаут. Иначе при отмене
  задачи ломался Shadow Git.
- **Секреты** (ключи API, токены аккаунтов, ключи приватных MCP) хранятся только зашифрованными через
  `vault` и никогда не возвращаются API целиком.

## 9. Состояние и что дальше

### Сделано и покрыто тестами
Всё из таблицы выше. `go test ./...` проходит, `go test -race ./internal/tasks` проходит.

### Не проверено на реальных сервисах (только на фейках)
- **Веб-чаты** (ChatGPT, Claude.ai, Gemini): селекторы на реальных аккаунтах не проверялись.
  Селекторы правятся без пересборки в `web-sites.json` в папке данных.
- **Настоящий Claude Code с MCP Edy** (`--mcp-config`, allowed/disallowed tools).
- **Импорт issue** с реального GitHub/GitLab/Gitea.
- **Уведомления macOS** (osascript) и **микрофон/диктовка** внутри окна Wails (ключи Info.plist добавлены).
- **Эмбеддинги** с настоящей Ollama или OpenAI (проверено на заглушке).

Первое, что стоит сделать новому разработчику на Mac, — пройти эти сценарии вручную и исправить
найденное.

### Следующие пункты плана владельца
1. **Картинки в веб-чатах** — следующий пункт. Нужно загружать вложения в ChatGPT, Claude.ai и Gemini
   через CDP (`DOM.setFileInputFiles` или вставка из буфера) и забирать сгенерированные изображения.
   Сейчас веб-адаптер передаёт только текст. Отправные точки: `internal/webchat/manager.go`,
   `internal/omniroute/web.go`, `cliimages.go` (как картинки передаются CLI).
2. После этого план, согласованный с владельцем, исчерпан. Идеи на будущее — в разделах «TODO» каждого
   документа.

### Как добавить новую возможность (чек-лист)
1. Хранение — новая таблица в `internal/store/<тема>.go` со своей константой схемы, подключённой в
   `store.Open` (см. [06-store.md](06-store.md)).
2. Логика — отдельный пакет в `internal/` с интерфейсами для зависимостей (как `memory.Store`,
   `semantic.Store`), чтобы тестировать без базы.
3. Подключение — опциональное поле в `tasks.Manager` / `api.Handler` / `agent.Task`, проводка в
   `internal/app/app.go`.
4. API — файл `internal/api/<тема>api.go` с методом `…Routes(m)` или регистрацией в `api.New`.
   Проверка проекта через `h.knownProject`.
5. Интерфейс — блок в `index.html` + функция `load…()`, вызов при смене проекта (`refreshProjectState`).
6. Тесты пакета и API; скриншоты обеих тем через временный `cmd/devui`.
7. Обновить `docs/ARCHITECTURE.md` и этот набор документов.
8. `gofmt`, `go vet`, `go test ./...`, проверка на секреты, удалить `cmd/devui`, локальный коммит.
   Push — только по команде.

## 10. Расхождения `docs/ARCHITECTURE.md` с кодом

`ARCHITECTURE.md` писался как журнал решений, и часть ранних планов реализована иначе:
