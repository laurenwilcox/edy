# План Edy: что сделано, что нет, и как работает каждая механика

Этот документ переносит план владельца. В нём три части:
- весь путь от первой концепции до текущего состояния;
- статус каждого пункта;
- описание каждой механики простыми словами: что она делает, как устроена внутри и где лежит код.

Подробности по коду — в документах 01–08. Здесь картина целиком.

Обозначения статуса: ✅ сделано и покрыто тестами · ⚠️ сделано частично или не проверено на настоящих
сервисах · ❌ не сделано.

## Часть 2. Как работает каждая механика

### M1. Запрос через OmniRoute
**Что делает.** Даёт любой программе один адрес в формате OpenAI для любой модели.
**Как устроено.**
1. Клиент шлёт `POST /v1/chat/completions` с `Authorization: Bearer <токен>` и `model: "провайдер/модель"`.
2. OmniRoute проверяет токен, находит провайдера в базе и проверяет дневной бюджет.
3. Запрос уходит адаптеру по виду провайдера (`openai`, `anthropic`, `cli`, `web`). Адаптер переводит
   формат и отдаёт ответ обратно в формате OpenAI, потоком (SSE) или целиком.
4. Расход считается по токенам и ценам провайдера и записывается с подписью клиента (`X-Edy-Client`).
Внутренние агенты Edy ходят в OmniRoute тем же путём, но без сети (`agent.InProcess`).
**Код:** `omniroute/server.go`. Подробно — 01-omniroute.md.

### M2. Ротация ключей
**Что делает.** Не даёт работе остановиться, когда у ключа кончился лимит.
**Как устроено.** У провайдера может быть несколько ключей. Ключ, получивший 429, «отдыхает» (по умолчанию
минуту, `defaultCooldown`), и запрос повторяется со следующим. Ключ, который провайдер отклонил как
неверный, отключается. Переключение незаметно, пока клиенту не ушёл первый байт ответа. Если сбой
случился посреди потока, запрос повторяется целиком: склеить ответ из двух генераций нельзя.
**Код:** `omniroute/server.go` (`cooldowns`, `coolingDown`).

### M3. Бюджет и расходы
**Что делает.** Ограничивает траты в долларах за сутки и показывает, кто сколько потратил.
**Как устроено.** Настройка `daily_budget_usd`. Перед каждым запросом сумма за сегодня сравнивается с
лимитом; при превышении возвращается 429 `budget_exceeded`. Каждая запись расхода содержит провайдера,
модель, токены, цену и клиента. Экран «Расходы» показывает их и статистику моделей.
**Код:** `omniroute/server.go` (`checkBudget`), `store`.

### M4. CLI-утилиты как модели
**Что делает.** Позволяет работать с моделями по подписке (Claude Code, Antigravity и др.) как с API.
**Как устроено.** Утилита запускается в виртуальном терминале (PTY) по шаблону команды с подстановками
`{model}` и `{prompt}`. Из вывода вырезаются цвета, спиннеры и прогресс-бары. Для Claude Code-исполнителя
OmniRoute добавляет `--mcp-config` с MCP Edy и запрещает ему собственные инструменты правки
(Bash/Edit/Write…), чтобы все правки шли через Edy и попадали в снимки. Картинки передаются утилите
файлами. Рабочая папка передаётся заголовком `X-Edy-Workdir`.
**Код:** `omniroute/cli.go`, `climcp.go`, `cliimages.go`, `sanitize.go`.

### M5. Веб-чаты
**Что делает.** Позволяет использовать подписки ChatGPT/Claude.ai/Gemini через их сайты.
**Как устроено.** Edy управляет видимым браузером через CDP: изолированный Chromium или установленный
Chrome с отдельным профилем на каждое подключение. Пользователь входит сам в обычном окне. Edy вставляет
текст, нажимает отправку, ждёт и забирает ответ. Ограничения: один запрос за раз, пауза 15 с между
запросами, до 150 запросов в день на сайт. При сбое сохраняются скриншот и описание страницы в
`web-debug/`. Селекторы правятся без пересборки в `web-sites.json`. Обхода защит нет и не будет.
Сейчас передаётся только текст (картинки — следующий пункт).
**Код:** `internal/webchat`, `omniroute/web.go`.

### M6. Эмуляция tools
**Что делает.** Делает агентом модель без вызова функций (CLI, веб-чат).
**Как устроено.** Если в запросе есть `tools`, OmniRoute вставляет в промпт их описание и протокол
`<tool_call>{"name":…,"arguments":…}</tool_call>`. Прошлые вызовы и результаты переводятся в текст.
Ответ модели разбирается обратно в `tool_calls` формата OpenAI. Для агента это выглядит как обычный API.
**Код:** `omniroute/toolemu.go`.

### M7. Теги возможностей
**Что делает.** Сообщает Edy, что умеет модель: `mcp`, `tools`, `vision`, `audio`, `voice`, `image_gen`,
`web`, `long_context`.
**Как устроено.** Теги задаются у провайдера (часть выводится из пресета). Оркестратор видит их у каждого
исполнителя и выдаёт MCP только тем, у кого есть `mcp`. Скриншоты получает только модель с `vision`,
голосовые — с `audio`.
**Код:** `omniroute/caps.go`.

### M8. Оркестратор
**Что делает.** Обсуждает задачу с пользователем и составляет план. Сам код не пишет.
**Как устроено.** В системный промпт попадают:
- исполнители с тегами и статистикой успеха и цены;
- скиллы;
- каталог MCP;
- выжимка памяти (похожие на задачу заметки и закреплённые);
- git-состояние;
- команда агентов;
- лимит параллельности.

Ответ разбирается так:
- блок `<plan>` — сам план;
- строки `MCP:`, `Скиллы:`, `Агент:` — что выдать исполнителю и кто его ведёт;
- `<subtasks>[…]</subtasks>` — деление на подзадачи (эпик);
- `<new_mcp>` — предложение добавить новый MCP-сервер.

В интерфейсе план показывается карточкой. Кнопка «Начать работу» ставит задачу на доску.
**Код:** `internal/orchestrator`, `api/projects.go`. Подробно — 03-orchestrator-board.md.

### M9. Исполнитель (агентный цикл)
**Что делает.** Выполняет задачу над папкой проекта.
**Как устроено.** Модель получает задачу, роль (если ведёт агент команды), выжимку памяти и список
скиллов. Дальше работает инструментами:
- поиск и чтение: `project_skeleton`, `search_code`, `list_files`, `read_file`;
- правка: `write_file`, `replace_in_file`, `delete_file`;
- память и скиллы: `project_memory`, `remember`, `use_skill`;
- завершение: `finish`.

После каждой правки делается снимок. Пути вне проекта, `.git` и `.edy` запрещены. Команд оболочки у
агента нет: проверки запускает сам Edy. За одну попытку — не больше 40 шагов модели (`MaxSteps`).
Исполнитель с тегом `mcp` (Claude Code) работает иначе: правит проект сам через MCP Edy, а Edy следит
за вызовами и делает снимки.
**Код:** `agent/task.go`, `agent/workspace.go`. Подробно — 02-agent.md.

### M10. Хуки (проверки)
**Что делает.** Проверяет результат после `finish`.
**Как устроено.** Проверки определяются по проекту: Go — `go vet` и `go test`, Python — `ruff` и `pytest`.
Свои проверки задаются в `.edy/hooks.json`. Таймаут — 10 минут. Если проверки упали, их вывод
(обрезанный) уходит модели с просьбой исправить.
**Код:** `agent/hooks.go`.

### M11. Circuit Breaker
**Что делает.** Не даёт модели бесконечно ломать проект.
**Как устроено.** После 3 провалов проверок подряд (`MaxAttempts`) проект откатывается к снимку №0, и
задача переходит к следующей модели в цепочке, которая начинает с чистого листа. Когда модели
кончились, статус «нужна помощь человека», проект в исходном состоянии.
**Код:** `agent/task.go`.

### M12. Shadow Git
**Что делает.** Хранит историю каждого шага агента, не трогая основной git.
**Как устроено.** Отдельный репозиторий `.edy/shadow.git` с рабочим деревом = папка проекта. Папка
`.edy` прячется от основного git через `.git/info/exclude`. Снимок №0 (baseline) делается перед
работой, дальше снимок после каждой правки. Возможности:
- откат к любому снимку;
- патч задачи для просмотра;
- откат одного файла.

Git-команды снимков не прерываются отменой задачи (`context.WithoutCancel` + таймаут 5 минут), иначе
остаётся `index.lock` и репозиторий портится. `Init` идемпотентен.
**Код:** `agent/shadow.go`.

### M13. Approve / Reject и запись в git
**Что делает.** Превращает результат в коммит по настройкам проекта или отменяет его.
**Как устроено.** Approve в зависимости от настройки проекта:
- новая ветка `edy/<задача>-<дата>` с одним коммитом — по умолчанию;
- коммит прямо в текущую ветку;
- без коммита.

После этого по настройке выполняется push и создаётся PR/MR. Если задача пришла из issue, коммит его
закрывает. Совпадение имён веток исключено (`agent.FreeBranch`). Задача без изменений принимается с
пометкой «изменений нет» (`agent.HasChanges`). Reject откатывает к снимку №0.
**Код:** `tasks/tasks.go` (`approve`, `Reject`), `api.Finalizer`, `internal/gitops`.

### M14. Вкладка Git
**Что делает.** Показывает git-состояние проекта, делает pull/push и задаёт настройки проекта.
**Как устроено.** Аккаунты GitHub/GitLab/Gitea с токенами (зашифрованы). В настройках проекта:
- режим коммита, push или PR, аккаунт;
- автор коммитов, префикс веток;
- автопринятие, модель ревьюера, сколько агентов эпика работают параллельно.

Настройки хранятся в `settings` под ключом `project:<путь>`. Клонирование репозиториев идёт в
`repos/` папки данных.
**Код:** `internal/gitops`, `api/gitapi.go`, `store/git.go`.

### M15. Доска задач и очередь
**Что делает.** Канбан проекта, на котором видна вся работа.
**Как устроено.** Колонки: Пул (`backlog`) → Очередь (`queued`) → В работе (`running`) → Ждёт решения
(`done`/`needs_human`/`failed`) → Готово (`approved`/`merged`; `rejected`/`cancelled` уходят в историю).
В одном проекте выполняется одна задача за раз, следующая из очереди стартует сама. У каждой карточки
лента событий: план, комментарии, смена модели, проверки, ревью, решения. Задачи хранятся в базе
(`board_tasks`, `board_events`). При запуске Edy `Recover()` откатывает задачи, оборванные прошлым
закрытием, и продолжает очереди.
**Код:** `tasks/tasks.go`, `store/board.go`, `api/projects.go`.

### M16. Автопринятие
**Что делает.** Позволяет очереди идти без человека, например ночью.
**Как устроено.** Если в настройках проекта включено `AutoApprove`, проверки прошли и ревьюер не нашёл
замечаний, Approve выполняется автоматически, и очередь идёт дальше.
**Код:** `tasks/tasks.go`, настройка в `store/git.go`.

### M17. Ревьюер
**Что делает.** Ищет то, что тесты не ловят.
**Как устроено.** После успешных проверок отдельная модель читает дифф задачи и выносит вердикт с
замечаниями. Модель задаётся во вкладке Git:
- «Автоматически» — резервная модель задачи;
- конкретная модель;
- «Без ревью».

С замечаниями автопринятие не срабатывает. Замечания одной кнопкой превращаются в новую задачу.
**Код:** `internal/review`, проводка в `internal/app/app.go`.

### M18. Просмотр изменений и файлов
**Что делает.** Показывает, что именно изменил агент, и любой файл проекта.
**Как устроено.** Патч задачи (до 400 КБ, `patchLimit`) хранится в задаче. Интерфейс показывает его по
файлам с подсветкой. Любой файл можно откатить к baseline (`RevertFile`). Файлы проекта открываются в
просмотрщике с собственной подсветкой синтаксиса (Go, Python, JS/TS, SQL, YAML и др.).
**Код:** `tasks/tasks.go`, `agent/shadow.go`, `api/projects.go`, функции подсветки в `index.html`.

### M19. Статистика моделей
**Что делает.** Помогает выбрать самую дешёвую модель, которая справляется.
**Как устроено.** По журналу агентов и расходам считается, сколько задач модель прошла и провалила и
сколько стоит одна успешная. Показывается на экране «Расходы». Оркестратор получает статистику в
контексте и советует модель.
**Код:** `store/agents.go` (`ModelStats`), `orchestrator`.

### M20. Уведомления
**Что делает.** Сообщает, что задача готова, у ревьюера замечания, нужна помощь или произошла ошибка.
**Как устроено.** Системное уведомление macOS через `osascript`. Отключается настройкой. На доске есть
кнопка проверки.
**Код:** `internal/notify`, проводка в `internal/app/app.go`.

### M21. Память проекта
**Что делает.** Агенты не повторяют ошибок и знают особенности проекта.
**Как устроено.** Заметки до 400 символов четырёх видов:
- факт;
- урок;
- итог задачи;
- заметка пользователя.

Что попадает в промпты (экономия токенов):
- закреплённые заметки видят все всегда;
- Оркестратор получает только похожие на задачу, около 500 токенов;
- исполнитель ищет сам инструментом `project_memory`, когда нужно.

Как память пополняется:
- агент записывает факты инструментом `remember` (не больше 5 за задачу);
- итоги и уроки задач Edy пишет сам, без вызова ИИ.

Поиск — BM25 с грубой основой слов. Если включён поиск по смыслу, результат смешивается с ним.
**Код:** `internal/memory`, `store/memory.go`, `api/memoryapi.go`.

### M22. Задачи из issue и шаблоны
**Что делает.** Ставит задачу по ссылке на issue и даёт частые задачи одной кнопкой.
**Как устроено.** По ссылке на issue GitHub/GitLab/Gitea Edy читает заголовок и текст через API аккаунта
и кладёт задачу в пул. Коммит после Approve содержит ссылку, закрывающую issue. Шаблоны задач встроены,
свои можно сохранять.
**Код:** `gitops/issue.go`, `api/projects.go`, `index.html`.

### M23. Скриншоты, голос, диктовка
**Что делает.** Позволяет показать баг картинкой и ставить задачи голосом.
**Как устроено.**
- **Картинки в чате и задачах.** Добавляются через 📎, вставку ⌘V или перетаскивание. Хранятся как
  `data:`-URL и в `attachments/` папки данных. Получает их только модель с тегом `vision`, остальным
  в ленте приходит предупреждение.
- **Диктовка 🎤.** Речь превращается в текст средствами браузера или macOS (Web Speech API), без ИИ и
  токенов.
- **Голосовое 🎙.** Звук уходит модели с тегом `audio`.

**Код:** `tasks/attachments.go`, `agent/llm.go` (`Msg.Images`), `index.html`.

### M24. Эпики (несколько агентов на одну задачу)
**Что делает.** Делит большую задачу между агентами, которые работают одновременно.
**Как устроено.** Оркестратор делит задачу на 2–6 подзадач и подбирает каждой модель или агента команды.
Зависимости задаются как «после N». Каждая подзадача идёт в своей копии проекта —
`git worktree` в `.edy/worktrees/<эпик>`. Одновременно работают до `MaxParallel` подзадач
(по умолчанию 2, максимум 6).

Порядок работы:
1. Готовая подзадача сливается в ветку эпика `edy/epic-<id>`; следующие стартуют уже с её изменениями.
2. Когда всё слито — общие проверки и ревью.
3. Approve — один раз на эпик, результат ложится в git по настройкам проекта (squash).

Конфликт слияния останавливает эпик и показывает, какая подзадача столкнулась. Reject удаляет копии.
При повторном планировании старые подзадачи снимаются (`Unsplit`). Эпик работает только в
git-проектах.
**Код:** `tasks/epic.go`, `tasks/worktree.go`.

### M25. Команда (постоянные агенты)
**Что делает.** Именованные агенты («Бэкенд», «Фронтенд»), которые копят опыт своей части проекта.
**Как устроено.** У агента есть:
- роль и зона (например `web/, *.css`);
- модель и резервная модель;
- скиллы и MCP, которые он получает всегда;
- личная память — заметки с полем `agent`.

Оркестратор видит команду и отдаёт задачу агенту, в чьей зоне она лежит, — строка `Агент:` в плане.
В начале задачи агент получает свои похожие на задачу заметки и общее закреплённое. Итог задачи
пишется и в общую, и в личную память.
**Код:** `store/team.go`, `api/teamapi.go`, `tasks/tasks.go` (`roleFor`, `memoryFor`).

### M26. Context Engine (карта проекта и поиск по словам)
**Что делает.** Агент не читает проект целиком, а смотрит карту и находит нужные куски.
**Как устроено.**
- **Скелет проекта.** Файлы, типы, функции и классы с номерами строк, без тел. Go разбирается
  `go/ast`, Python — встроенным скриптом через `python3 -I`. Если Python нет, объявления ищутся по
  строкам.
- **Поиск по словам.** BM25 по кускам кода. Для Go и Python кусок — это объявление, для остальных
  файлов — блок строк. Идентификаторы разбиваются на слова: `parseRequest` → parse, request.
- **Кто пользуется.** Скелет получают Оркестратор и агент, пользователь видит его в «Карте проекта».

**Код:** `internal/codeindex`.

### M27. Поиск по смыслу
**Что делает.** Находит код по смыслу: «где проверяется пароль» → `checkCredentials`.
**Как устроено.**
1. **Векторы.** Модель эмбеддингов (настройка `embed_model`, OpenAI-совместимый провайдер, например
   `ollama/nomic-embed-text`) превращает куски кода и заметки памяти в векторы через
   `/v1/embeddings` OmniRoute.
2. **Хранение.** Векторы лежат в таблице `embeddings`. Вектор находится по хешу текста, поэтому
   пересчитываются только изменённые куски.
3. **Обновление.** Перед каждой задачей индекс обновляется сам, не дольше минуты.
4. **Поиск.** `search_code` и `project_memory` смешивают результаты BM25 и векторов через reciprocal
   rank fusion. Если модель недоступна, остаётся поиск по словам.

**Код:** `internal/semantic`, `omniroute/embeddings.go`, `store/embeddings.go`, `api/semanticapi.go`.

### M28. MCP-сервер Edy
**Что делает.** Даёт внешним агентам (Claude Code, Cursor, Gemini CLI) инструменты Edy.
**Как устроено.**
- **Подключение.** По stdio (`edy mcp -project …`) или по HTTP (`/mcp?project=…` с токеном).
- **Инструменты.** Те же, что у агента: скелет, поиск, чтение, правка, проверки, скиллы, память.
- **Снимки и журнал.** Каждая правка — снимок в Shadow Git. Внешний клиент виден в окне «Агенты».
- **Во время задачи** правки через MCP от посторонних клиентов запрещены (`Busy`). Исполнитель самой
  задачи получает отдельную привязку (`bind=key`), его правки разрешены и попадают в ленту задачи.

**Код:** `internal/mcp`, `api/mcpapi.go`, `cmd/edy/mcp.go`. Подробно — 04-mcp.md.

### M29. Каталог MCP-серверов
**Что делает.** Хранит внешние MCP-серверы, которые Оркестратор может выдать исполнителю.
**Как устроено.** У сервера есть:
- имя, описание («для чего»), аккаунт;
- команда или адрес;
- секреты, которые хранятся зашифрованными и не возвращаются API.

Оркестратор пишет нужные серверы в строке `MCP:`. Исполнитель с тегом `mcp` получает их вместе с MCP
Edy (заголовок `X-Edy-MCP-Servers`). Если подходящего сервера нет, Оркестратор предлагает новый
(`<new_mcp>`), и пользователь добавляет его одной кнопкой.
**Код:** `api/mcpcatalog.go`, `store/mcpservers.go`, `omniroute/climcp.go`.

### M34. Микро-агенты
**Что делает.** Разовая узкая задача на дешёвой модели со строгим JSON-ответом.
**Как устроено.** Задача описывает схему полей (тип, обязательность, enum, границы). Ответ проверяется
`micro.Validate`; если он не прошёл, модель получает описание ошибки и отвечает снова (до 3 попыток).
Модель берётся из настройки `micro.model`, иначе — самая дешёвая (API и CLI важнее веб-чатов).
Каждый запуск пишется в журнал агентов с ролью `micro`.

### M35. UI-бот
**Что делает.** Меняет оформление по просьбе обычными словами («сделай тёмную тему и шрифт покрупнее»).
**Как устроено.** Бот — микро-агент, который знает только белый список полей: тема, акцент, шрифт,
размер шрифта (12–18), сторона меню, анимации. CSS и JS он не видит и не правит. Настройки хранятся
в `ui.prefs` и применяются через `data-*` атрибуты и `--fs`. Их же можно менять вручную в панели «Оформление».

### M30. Скиллы
**Что делает.** Даёт готовые инструкции проекта («как у нас пишут тесты»).
**Как устроено.** Скилл — это `<имя>/SKILL.md` с заголовком `name`/`description`, формат Claude Code.
Лежит в `skills/` папки данных (общие) или в `.edy/skills/` проекта; скилл проекта важнее общего.

Как скиллы доходят до агента:
- Оркестратор выдаёт только нужные (строка `Скиллы:`);
- агент видит их список и загружает нужный через `use_skill`;
- внешние агенты получают скиллы по MCP.

**Код:** `internal/skills`.

### M31. Журнал агентов
**Что делает.** Показывает, кто что делал и с каким результатом.
**Как устроено.** Каждый агент — запись в `agents`: роль, модель, проект, цель, статус. Его события
(вызовы инструментов, снимки, ошибки) пишутся в `agent_events`. При запуске Edy агенты прошлого запуска
помечаются прерванными. Окно «Агенты» показывает журнал.
**Код:** `store/agents.go`.

### M32. Безопасность
- **Доступ.** OmniRoute и API слушают только `127.0.0.1` и требуют Bearer-токен. Токен лежит в
  `router.token` (права 0600). Интерфейс получает его через `#token=…` в адресе, и браузер не отправляет
  эту часть на сервер.
- **Секреты.** Ключи API, токены аккаунтов и секреты MCP шифруются AES-GCM. Мастер-ключ лежит в Keychain.
- **Изоляция агента.** Агент не выходит за папку проекта: нет абсолютных путей, `..`, `.git`, `.edy`,
  символических ссылок наружу и команд оболочки.
- **Ограничение API.** Работа только с проектами, известными Edy (`knownProject`).
- **Интерфейс.** CSP запрещает внешние скрипты; картинки и звук разрешены только из `data:` и `blob:`.

### M33. Восстановление после перезапуска
- Задачи в состоянии `running` при запуске откатываются, и очереди продолжаются (`tasks.Recover`).
- Копии эпиков (worktree) убираются.
- Агенты прошлого запуска помечаются прерванными (`InterruptRunningAgents`).

**Код:** `tasks/tasks.go`, `internal/app/app.go`.
