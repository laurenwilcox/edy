# 03. Оркестратор и доска задач

Документ для разработчика, который принимает проект. Охватывает:

- `internal/orchestrator/` — Оркестратор (планирует, сам код не пишет);
- `internal/tasks/` — доска задач: пул, очередь, выполнение, ревью, Approve/Reject, эпики, вложения;
- `internal/review/` — ревьюер перед Approve;
- `internal/notify/` — уведомления macOS;
- `internal/gitops/` — git-операции, push, PR/MR, импорт issue;
- обработчики API, которые этим управляют: `internal/api/projects.go`, `gitapi.go`, `teamapi.go`, `memoryapi.go`.

Полный список HTTP-маршрутов есть в отдельном документе. Здесь описано **поведение** и связи между частями.
Ссылки `файл:строка` даны по состоянию кода на момент написания (последний коммит `b88fcbf`).
После правок номера строк могут сместиться, поэтому ищите по имени функции.

Связанные пакеты, которые здесь только упоминаются: `internal/agent` (цикл агента, хуки, Shadow Git, Circuit Breaker),
`internal/store` (SQLite), `internal/memory` (память проекта), `internal/skills`, `internal/semantic`, `internal/omniroute`.

## 2. Жизненный цикл запроса пользователя

### 2.1. Общая схема

```
 Пользователь                 API (internal/api)                    tasks.Manager                     agent / git
 ────────────                 ──────────────────                    ─────────────                     ───────────
 пишет в чат ───────────► POST /api/orchestrator
                          orchestrate() projects.go:233
                            ├─ orchestratorContext()  (модели, caps, stats, skills, MCP)
                            ├─ teamMembers(), MaxParallel, memory.Brief
                            └─ orchestrator.Chat() ── LLM (без tools) ──► Reply{Text, Plan, MCP, Skills, Agent, Subtasks, NewMCP}
 видит план, жмёт
 «Начать работу» ───────► POST /api/tasks  startTask() projects.go:451
                            ├─ PlanMCP / PlanSkills повторно (по тексту плана)
                            ├─ агент команды → его модели, union MCP/скиллов
                            ├─ Unsplit (если новый план без деления)
                            └─ Enqueue(...)  или  EnqueueEpic(...)
                                                               ├─ state = queued, событие «queued»
                                                               └─ kick(project) ── проект свободен? ──► work() / runEpic()
                                                                                                         │
                                                                                         agent.Task.Run ◄┘  (Shadow Git снимок №0,
                                                                                                             шаги модели, хуки, Circuit Breaker)
                                                               ◄── Result{Status, Summary, Diff, Baseline}
                                                               ├─ done        → Patch, review(), автопринятие?, notify
                                                               ├─ needs_human → урок в память, notify
                                                               ├─ failed      → notify
                                                               └─ cancelled   → откат к Baseline
 смотрит diff, жмёт
 Approve ───────────────► POST /api/tasks/{id}/approve ──► approve()
                                                               ├─ (эпик) applyEpic: git merge --squash edy/epic-…
                                                               ├─ HasChanges? нет → «коммит не нужен»
                                                               └─ Finalize = api.Finalizer → gitops.Finalize
                                                                     (ветка edy/… | direct | none, push, PR)
                                                               state = approved, итог в память, kick → следующая
 или Reject ────────────► …/reject ──► Reject(): откат к Baseline (или удаление worktree эпика), state = rejected, kick
```

### 2.2. Пошагово

1. **Чат с Оркестратором.** UI шлёт `POST /api/orchestrator` с полями `project`, `model` (модель Оркестратора), `messages` (вся история), `conversation` (id разговора для журнала) и `executors` (выбранный исполнитель и резерв). Обработчик `orchestrate` находится в `projects.go:233`:
   - отбрасывает из истории всё, кроме ролей `user` и `assistant` (`projects.go:253-258`);
   - ведёт Оркестратора в журнале агентов как `orch-<conversation>` (`journalOrchestrator`, `projects.go:404`). Если id пустой, длиннее 64 символов или содержит пробел или `/`, журнал не ведётся;
   - собирает `orchestrator.Context` (см. §3.2), ставит таймаут 10 минут;
   - вызывает `orchestrator.Chat` и пишет в журнал текст, план, выданные MCP, скиллы и назначенного агента.
   - Ответ — JSON `orchestrator.Reply`. Сам по себе он ничего не создаёт на доске.
2. **Утверждение плана.** Кнопка «Начать работу» шлёт `POST /api/tasks` (`startTask`, `projects.go:451`) с полями `plan`, `request`, `models`, `subtasks`, `comment` и опционально `id` (если задача из пула), `agent` (агент команды, выбранный вручную), `parent`.
3. **Постановка в очередь.** `Manager.Enqueue` (`tasks.go:326`) или `Manager.EnqueueEpic` (`epic.go:59`). Состояние становится `queued`, в историю пишутся события `plan` и `queued`.
4. **Запуск.** `kick(project)` (`tasks.go:389`) берёт первую по порядку обхода задачу в `queued`, если в проекте ничего не выполняется и нет результата в `done`, который ждёт решения. Обычная задача запускается через `work()`, эпик — через `runEpic()`.
5. **Выполнение.** `execute()` (`tasks.go:999`) собирает `agent.Task` и вызывает `Run`. Внутри Run: `CheckClean`, `excludeEdyDir`, определение хуков, снимок №0 в Shadow Git, затем модели по цепочке (Circuit Breaker). Подробности — в документе про агента.
6. **Хуки.** Проверки (`go test`, ruff/pytest, `.edy/hooks` и т.п.) запускает агент после `finish`. Доска видит их как события `hooks` с символами `✓`/`✗`. По ним `lastFailure` (`tasks.go:528`) извлекает причину провала для урока в памяти.
7. **Итог.** `work()` (`tasks.go:545-589`) переводит задачу в `done`, `needs_human`, `failed` или `cancelled`. Для `done` сохраняется полный patch (до 400 КБ) и вызывается `afterDone` (ревью, автопринятие, уведомление).
8. **Решение.** `Approve` (`tasks.go:708`) или `Reject` (`tasks.go:775`). После решения запускается `kick`: очередь продолжается.
9. **Оформление.** `Finalize` создаёт ветку `edy/<slug>-MMDD-HHMM` (свободное имя через `agent.FreeBranch`), коммитит, затем по настройкам делает push и PR. Подробности — в §9.
10. **`merged`.** Это состояние бывает только у **подзадачи эпика**: её результат слит в общую ветку эпика (`epic.go:330-333`). У обычной задачи финальное состояние — `approved`.

## 3. Оркестратор (`internal/orchestrator`)

### 3.1. Что он решает

Оркестратор — это один вызов LLM без инструментов (`orchestrator.go:242`, передаётся `tools=nil`). Он:

- задаёт 1–3 уточняющих вопроса или выдаёт план в `<plan>…</plan>`;
- выбирает **скиллы** строкой `Скиллы: a, b` внутри плана;
- выбирает **внешние MCP-серверы** из каталога строкой `MCP: x, y`, но только если основной исполнитель умеет MCP;
- может **предложить** новый MCP-сервер блоком `<new_mcp>{json}</new_mcp>`. Добавляет его пользователь, Оркестратор только предлагает;
- назначает **агента команды** строкой `Агент: имя`;
- если проект в git, может **разбить задачу** на 2–6 подзадач блоком `<subtasks>[…]</subtasks>` и выбрать модель для каждой;
- советует **сменить модель**, если исполнитель чего-то не умеет (картинки, звук, интернет) или статистика показывает модель дешевле или надёжнее. Это только текстовый совет, автоматически модель не меняется.

Модель **основного** исполнителя Оркестратор сам не выбирает: её выбирает пользователь в UI (`executors`), а при `startTask` передаются `models`. Модели Оркестратор выбирает только для подзадач и косвенно через агента команды (у агента своя модель).

### 3.2. `Context` и его сборка

`orchestrator.Context` (`orchestrator.go:76`):

| Поле | Откуда берётся (API) | Смысл |
|---|---|---|
| `Executors []Executor` | `orchestratorContext(project, req.Executors)` (`projects.go:305`) | Выбранный исполнитель и резерв Circuit Breaker. Первый — основной. Пусто — исполнитель ещё не выбран. |
| `Others []Executor` | все модели всех провайдеров, кроме выбранных, **не больше 30** (`projects.go:337-344`) | Чтобы Оркестратор мог посоветовать замену и выбрать модели подзадачам. |
| `Skills []Skill` | `skills.Load(skills.Dirs(h.Home, project))` | Общие скиллы и скиллы проекта (`.edy/skills`). |
| `Servers []Server` | `orchestratorServers()` (`projects.go:384`) — только **включённые** серверы каталога MCP | Имя, описание и аккаунт. |
| `Memory string` | `memory.Brief(notes, последняя реплика, 2000)` (`projects.go:268-271`) | Закреплённое и похожее на просьбу, примерно 500 токенов. |
| `Git bool` | `gitops.IsRepo(project)` | Можно ли делить задачу на подзадачи. |
| `Parallel int` | `ProjectSettings.MaxParallel` | Сколько агентов эпика работают одновременно (0 значит 2). |
| `Team []Member` | `teamMembers(project)` (`teamapi.go:140`) — только `Enabled` | Имя, роль (первое предложение), зона, модель и статистика. |

`Executor` (`orchestrator.go:66`) содержит `Model` (`провайдер/модель`), `Caps` (заголовки тегов возможностей провайдера через `omniroute.CapTitle`, например «Картинки»), `MCP bool` (провайдер имеет cap `omniroute.CapMCP`) и `Stats`.
`Stats` формирует `statLine` (`projects.go:355`), например «за 30 дней прошла проверки в 4 из 5 задач, ≈$0.12 за успешную задачу» или «без оплаты за токены (подписка или локальная)».

**Как теги возможностей ограничивают решения:**

- MCP. В промпте при `!Executors[0].MCP` пишется «строку MCP не пиши» (`orchestrator.go:205-207`). После ответа `out.MCP` заполняется **только** если `Executors[0].MCP` (`orchestrator.go:247-249`). Без выбранного исполнителя MCP не выдаётся вообще.
- Скиллы выдаются всегда (`orchestrator.go:250`): исполнитель без MCP получает их в промпте, с MCP — через MCP Edy (`capsLine`, `orchestrator.go:122-136`).
- Картинки и прочее. Теги перечислены у каждой модели, и промпт требует посоветовать модель, которая это умеет (`orchestrator.go:161`). Само исполнение проверяет зрение через `Manager.CanSee` (`app.go:123-127`, cap `CapVision`).
- Подзадачи. Модель подзадачи должна быть из `Executors ∪ Others`, иначе подставляется первая известная модель (`checkSubtasks`, `orchestrator.go:262-298`).

### 3.3. Системный промпт (дословно)

Основа (`orchestrator.go:18-35`). `%s` — путь проекта и скелет проекта (`codeindex.Build(...).Skeleton(15000)`):

```text
Ты — Оркестратор Edy. Ты не пишешь код сам: ты обсуждаешь задачу с разработчиком и готовишь план для агента-исполнителя.

Как работать:
- Если задача понятна не до конца, задай 1–3 коротких уточняющих вопроса.
- Когда всё ясно, составь короткий план и выведи его блоком:
<plan>
Задача: одно предложение, что нужно сделать.
1. Первый шаг (какие файлы и что в них поменять).
2. …
Проверка: как убедиться, что всё работает (какие тесты добавить или запустить).
</plan>
- Вне блока объясни план в 1–2 предложениях. Разработчик утвердит его кнопкой «Начать работу» или попросит поправить.
- Опирайся на реальную структуру проекта ниже, не выдумывай файлы.
Отвечай по-русски, кратко.

Проект: %s
Скелет проекта (файлы, типы и функции без тел):
%s
```

К основе добавляется `instructions(c)` (`orchestrator.go:139-227`). Разделы идут в таком порядке:

1. *(если есть память)* `Память проекта (закреплённое и похожее на эту задачу) — учитывай в плане:` и выжимка.
2. `Исполнитель и его возможности.` Дальше либо «Исполнитель ещё не выбран: не выдавай MCP-серверы, скиллы выдавать можно.», либо «Задачу выполнит (первый — основной, дальше — резерв Circuit Breaker):» со строками вида
   `- провайдер/модель: Картинки, Инструменты; скиллы получает через MCP Edy; за 30 дней прошла проверки в 3 из 4 задач, ≈$0.10 за успешную задачу`.
3. `Другие доступные модели:` в том же формате.
4. Две фиксированные строки: про модель, которая умеет нужное (картинки, звук, голос, интернет), и про замену по статистике (дешевле или реже проваливается).
5. *(если есть команда)*
   ```text
   Команда проекта — постоянные агенты. У каждого своя роль, зона и память о прошлых задачах в этой зоне, поэтому задачу из его зоны лучше отдать ему. Назначь агента строкой в плане:
   Агент: имя
   В подзадачах — полем "agent":"имя" (модель агента подставится сама). Если задача ни в чьей зоне, агента не назначай.
   - Имя (модель): первое предложение роли; зона: web/, *.css; сделал 5 задач, не справился с 1
   ```
6. *(если есть скиллы)* `Скиллы — инструкции проекта. Выдай исполнителю только те, что относятся к задаче, отдельной строкой в плане:\nСкиллы: имя1, имя2\nЕсли ни один не нужен, строку не пиши.\nДоступные скиллы:` и список `- имя — описание`.
7. Если `Git`:
   ```text
   Несколько агентов. Если задача большая и делится на независимые части (разные файлы или модули), раздели её
   на 2–6 подзадач: их сделают разные агенты одновременно (до %d сразу), каждый в своей копии проекта, потом Edy
   сольёт результат и прогонит общие проверки. Простую задачу или задачу, где все правки в одном месте, не дели.
   Части не должны править одни и те же строки — иначе будет конфликт. Каждой подзадаче выбери исполнителя из
   моделей выше по возможностям и статистике: простое — дешёвой модели, сложное — сильной. Если часть зависит от
   другой, укажи её номер в after (только меньшие номера). Блок — после плана:
   <subtasks>[{"title":"коротко","goal":"что сделать и в каких файлах","model":"провайдер/модель","after":[1]}]</subtasks>
   ```
   Иначе: `Проект без git: задачу на подзадачи для нескольких агентов не дели.`
8. `MCP-серверы.` Если основной исполнитель не умеет MCP: «Основной исполнитель не умеет MCP: строку MCP не пиши.», и на этом промпт заканчивается. Иначе текст про MCP Edy, который выдаётся всегда, правило «дополнительные серверы — только если без них задачу не сделать или не проверить», строка `MCP: имя1, имя2`, список каталога (`- имя — описание (аккаунт: …)`) или «Каталог MCP-серверов пуст.», и в конце инструкция про `<new_mcp>{"name":…,"type":"stdio","command":"npx","args":[…],"secrets":…}</new_mcp>` (для удалённого сервера `"type":"http","url":…`) с оговоркой «Не выдумывай пакеты и адреса».

### 3.4. Разбор ответа

`Chat` (`orchestrator.go:230-258`): `codeindex.Build`, затем LLM, затем `parse`, затем пост-обработка.

`parse` (`orchestrator.go:348-369`):

1. Каждый `<new_mcp>` разбирается как JSON `Proposal`. Принимается, только если есть `name` и либо `type=stdio` с `command`, либо `type=http` с `url`. Все блоки вырезаются из текста.
2. **Первый** `<subtasks>` разбирается как `[]Subtask` (ошибка JSON молча игнорируется). **Все** блоки `<subtasks>` вырезаются.
3. `<plan>` — первый блок становится `Plan`. Текст вне него, с вырезанными всеми `<plan>`, становится `Text`. Если плана нет, весь ответ идёт в `Text`.

Пост-обработка:

- `PlanMCP(plan, servers)` (`orchestrator.go:331`) берёт строки `MCP:` из **плана** (regex `(?mi)^\s*[-*]?\s*MCP\s*:\s*(.+)$`) и оставляет только имена из каталога. Регистр игнорируется, имя приводится к каноническому, дубликаты убираются, кавычки, звёздочки и «ёлочки» обрезаются (`pick`, `orchestrator.go:309-327`). Разделители: `,`, пробел, `;`. Значит, **имена с пробелами не поддерживаются**.
- `PlanSkills` работает так же со строкой `Скиллы:` или `Skills:`.
- `PlanAgent(plan, team)` (`orchestrator.go:380`) берёт **первую** строку `Агент:` или `Agent:`. Имя сравнивается без учёта регистра (`memberName`). Неизвестное имя даёт пустую строку.
- `checkSubtasks` (`orchestrator.go:262`):
  - пропускает подзадачи с пустым `goal`;
  - ограничивает список шестью;
  - нормализует `agent`;
  - модель не из `Executors ∪ Others` заменяет на `fallback` (первый исполнитель, иначе первая из Others);
  - оставляет в `after` только номера `1..len(out)`, то есть ссылки только на более ранние;
  - пустой `title` заменяет на `goal`;
  - **если осталось меньше двух подзадач, возвращает nil** (задача не делится).
- Без git `Subtasks = nil`.

`Goal(request, plan)` (`orchestrator.go:372`) собирает задание исполнителю: `просьба + "\n\nУтверждённый план:\n" + план`.

**Важно.** Строки `MCP:`, `Скиллы:` и `Агент:` ищутся **только внутри плана**, а не во всём ответе. В `startTask` они разбираются **заново** из текста `req.Plan`, который прислал клиент (`projects.go:485-492`, `515`). Поэтому пользователь может поправить план в UI, и выданные скиллы и MCP изменятся. Но есть отличие: `startTask` **не проверяет MCP-возможность** исполнителя, в отличие от `Chat`. Ограничение там срабатывает только на уровне агента: `agent.Task` выдаёт `Extra` лишь моделям, которые поддерживают MCP, остальные получают событие «не умеет MCP: серверы … не выданы» (`internal/agent/task.go:178-183`).

## 4. Доска задач (`internal/tasks`): данные

### 4.1. Хранение

- Интерфейс `Board` (`tasks.go:34`) реализует `*store.Store`. Таблица карточек: `store.BoardTask{ID, Project, Parent, Title, Data, State, Position, Created, Updated}`, где `Data` — JSON всего `record`. История карточки — `BoardEvent{ID, Kind, Text, At}`.
- `record` (`tasks.go:123`) = `View` + служебные поля:
  - `Baseline` — id снимка Shadow Git до задачи;
  - `AllSkills` — задача без Оркестратора получает все скиллы;
  - `Patch` — полный diff, до 400 КБ (`patchLimit`, `tasks.go:140`);
  - `EpicBase` и `EpicBranch` — у эпика, `SubBranch` — у подзадачи.
- `load` (`tasks.go:199`) берёт колонки таблицы (ID, Project, Parent, Title, State, Position, Created, Updated) **поверх** JSON. Источник правды по этим полям — колонки.
- `save` (`tasks.go:218`) всегда выставляет `Updated = Now()`.
- `update(id, fn)` (`tasks.go:238`) делает load, fn, save под `m.mu`. **Любое изменение карточки после создания должно идти через `update`**, иначе возможна гонка с горутиной задачи.
- `event` (`tasks.go:229`) пишет в историю карточки, а если есть `agentID` и `Journal`, то и в журнал агента.
- id карточки — `task_` и 12 hex-символов (`newID`, `tasks.go:965`). От этого формата зависит проверка путей вложений (`attachDir`).
- Заголовок — заданный или первая строка просьбы, не длиннее 90 рун (`titleOf`, `tasks.go:977`).
- `Position` задаёт порядок в колонке: при создании и постановке в очередь это `UnixMilli`. `List` сортирует по нему (`tasks.go:682`).

## 5. Очередь (`kick`)

`kick(project)` (`tasks.go:389-463`) выполняется **целиком под `m.mu`**:

1. Если в `m.active[project]` уже есть run, выходим. **Правило: одна выполняющаяся задача (или эпик) на проект.**
2. Проходит все карточки проекта (`BoardTasks`, порядок задаёт store).
   - Встретили `done` — выходим: **пока результат ждёт решения, очередь стоит.** На этом держится правило «следующая стартует после решения по предыдущей».
   - Первая `queued`, которая не подзадача (`KindSub`), становится кандидатом. Подзадачи запускает сам эпик.
3. `agent.CheckClean(project)`. Если не прошёл, кандидат уходит в `failed` с текстом ошибки, событие и уведомление отправляются в отдельных горутинах (`go m.event`, `go m.notify`). **Очередь при этом не продолжается**: следующие задачи упали бы по той же причине. Возобновится она при следующем `kick`: новый Enqueue, Approve или Reject, перезапуск.
4. Эпик: `running`, `m.active[project] = run`, `running.Add(1)`, `go runEpic`.
5. Обычная задача:
   - загружает скиллы `skills.Load(skills.Dirs(SkillsHome, project))`;
   - если не `AllSkills`, оставляет только названные;
   - **перезаписывает `r.Skills` фактическими именами** (у задачи без Оркестратора там окажутся все скиллы);
   - сохраняет `running` и запускает `go m.work(ctx, run, r, skills)`.

Кто вызывает `kick`:

- `enqueue` (если `start=true`);
- `EnqueueEpic` (`go`);
- `work()` в конце;
- отложенная функция в `runEpic`;
- `approve` (не в авто-режиме, `go`);
- `Reject` (`go`);
- `Recover` — по всем проектам.

`StartWith` (`tasks.go:375`) — постановка «сразу в работу» без пула (CLI `edy task`, API без плана). Если проект грязный и в нём ничего не выполняется, сразу возвращается ошибка. Если что-то выполняется, задача просто встаёт в очередь. `Start` — то же со всеми скиллами (`Options{}` ⇒ `Skills == nil` ⇒ `AllSkills`).

## 6. Выполнение (`work` / `execute`)

`execute(ctx, ru, r, root, goal, given)` (`tasks.go:999-1075`) используется и обычной задачей, и подзадачей эпика. У подзадачи `root` — это её worktree. Собирается `agent.Task`:

| Поле Task | Значение |
|---|---|
| `Root`, `Goal`, `Models` | папка (проект или worktree), задание, цепочка моделей |
| `LLM` | `m.LLM` (OmniRoute, клиент `agent`) |
| `Skills` | выданные скиллы (`[]skills.Skill`) |
| `MCP`, `Extra` | мост MCP Edy и внешние серверы из каталога, выданные планом (`r.MCP`) |
| `Memory`, `MemoryBrief` | `memoryFor(r)` (`tasks.go:466`): `memory.Access{Source:"task:<id>", Agent:r.Agent}` с `Ranker` семантики, если она есть. Brief — `AgentBrief(...,2000)` для агента команды, иначе `Pinned(...,1500)`. |
| `Code` | `codeSearch` (`tasks.go:483`): **перед задачей** обновляет семантический индекс проекта (до 1 минуты, ошибка не мешает) и возвращает `semantic.Code`. При `m.Semantic == nil` или пустой модели эмбеддингов — `nil`. |
| `Images`, `CanSee` | `images(r)` (`attachments.go:124`), не больше 4 картинок; `m.CanSee` |
| `Role` | `roleFor(r)` (`tasks.go:494`): инструкции агента команды (см. §8) |
| `MaxAttempts` | `m.maxAttempts` (0 — по умолчанию 3 в agent) |
| `OnEvent` | Каждое событие агента идёт в историю карточки. Если агент уже создан, оно же идёт в журнал агента. События **до** первого `OnAttempt` копятся в `ru.pending` и переносятся в журнал при создании агента. |
| `OnAttempt` | Каждая модель в цепочке — **отдельный агент журнала** с id `<taskID>-<n>`, роль `RoleExecutor`. Со второй попытки в историю пишется «Модель сменилась: задачу взяла …». id дописывается в `r.Agents` через `update`. |
| `OnAttemptEnd` | `FinishAgent`: `done`, `cancelled` («остановлен пользователем») или `failed` с заметкой. |

`ru.agentID` и `ru.pending` защищены локальным `agentsMu`, потому что колбэки агента могут прийти из другой горутины (MCP-сервер).

`work` (`tasks.go:545-589`) после `execute`:

- `cancelled`: откат `agent.Reject(context.Background(), project, Baseline)`. Контекст фоновый: отменённый ctx уже мёртв.
- `failed`: событие `error`, уведомление «Ошибка: …».
- `needs_human`: урок в память (`lastFailure`), уведомление «Нужна помощь: ни одна модель не справилась, проект откачен».
- `done`: `afterDone`.
- Затем `delete(m.active, project)` и `kick`.

Обратите внимание: при `failed` проект **не откатывается**. Обычно это безопасно: `agent.Task.Run` возвращает `err` только при ошибках самого Edy (снимок, git, отмена). Ошибки LLM считаются провалом попытки, а не `err`. Но если снимок упал посреди работы, в проекте могут остаться правки. Тогда следующая задача упадёт на `CheckClean`, а откатиться можно через «Проект → снимки» (`/api/projects/restore`).

## 7. После готовности: ревью, автопринятие, уведомления

### 7.1. `afterDone` (`tasks.go:592-612`)

1. `review(r, agentID)`. Результат сохраняется в `r.Review`.
2. Если `AutoApprove(project)` и (`Review == nil` или `Verdict == "ok"`):
   - пишется событие «Автопринятие: проверки и ревью прошли»;
   - вызывается `approve(id, auto=true)`. В авто-режиме `approve` **не** вызывает `kick`: это сделает `work`/`runEpic`;
   - при успехе уведомление «Готово и принято автоматически: <note>»;
   - при ошибке событие «Автопринятие не удалось: …», и задача остаётся `done`.
   - Вердикты `issues` и `error` автопринятие **блокируют**.
3. Иначе уведомление «Готово — проверьте и примите (Approve) или отклоните» или «Готово, но у ревьюера есть замечания — посмотрите перед Approve».

### 7.2. `review` (`tasks.go:615-641`)

- `m.Review == nil` → ревью нет.
- Таймаут 15 минут. Patch обрезается до **60 КБ** с пометкой.
- Ошибка ревьюера даёт `Verdict: "error"`, а пустой `Verdict` без ошибки означает, что ревью выключено, и функция возвращает `nil`.
- В историю пишется событие `review`: «замечаний нет», «есть замечания\n…» или «Ревью не удалось: …».

### 7.3. Ревьюер (`internal/review`)

Промпт (`review.go:17-30`, дословно):

```text
Ты — ревьюер кода в Edy. Тебе дают задачу, утверждённый план и изменения (diff).
Линтеры и тесты уже прошли. Ищи то, что они не ловят:
- ошибки логики и неучтённые крайние случаи;
- расхождение с задачей и планом, лишние или незаконченные изменения;
- проблемы безопасности (секреты в коде, инъекции, небезопасные права);
- новую логику без тестов.
К стилю и вкусовщине не придирайся.

Ответь строго в формате. Первая строка:
ВЕРДИКТ: OK
или
ВЕРДИКТ: ЗАМЕЧАНИЯ
Если есть замечания — дальше нумерованный список, не больше 7 пунктов: файл — проблема — что сделать.
Отвечай по-русски, кратко.
```

Пользовательское сообщение (`review.go:51-56`) содержит `Задача:\n<Goal>`, затем `Итог исполнителя (<model>): <summary>` и `Изменения:` в блоке ```diff.
Обратите внимание: промпт упоминает «утверждённый план», но отдельно план не передаётся. Он виден только внутри `Goal`, потому что `orchestrator.Goal` вклеивает его туда.

Выбор модели (`app.go:129-139`, функция `Pick`):

- `ProjectSettings.ReviewModel == "off"` → `""`, ревью нет;
- `""` (по умолчанию) → `review.AutoModel(v)` (`review.go:99`): **первая модель цепочки, отличная от той, что справилась**, обычно резервная; если цепочка из одной модели, та же модель;
- иначе указанная `провайдер/модель`. Её валидирует `gitSettings` (`gitapi.go:231-239`): формат и существующий провайдер.

`New` (`review.go:38-78`):

- пустой patch даёт `ok` с текстом «Изменений нет — проверять нечего.»;
- в журнале создаётся агент `<taskID>-review` с ролью `RoleReviewer`;
- вызов LLM без инструментов;
- `Parse`.

`Parse` (`review.go:80-96`):

- regex `(?i)ВЕРДИКТ\s*:\s*\**\s*(OK|ОК|ЗАМЕЧАНИЯ|ISSUES)`. Латинское OK и кириллическое ОК оба означают `ok`, допускается `**жирный**`.
- Нет вердикта, но есть текст → **`issues`**: автопринятие не должно пройти по непонятному ответу.
- Пустой ответ → `error`.
- Текст после вердикта идёт в `Text`.

Ревьюер используется и для эпиков: `runEpic` вызывает `afterDone(final, "")` на общем patch.

### 7.4. Уведомления (`internal/notify`)

- `notify.System(title, msg)` (`notify.go:27`): только на `darwin`, на других системах это no-op. Запускает `osascript -e <script> <title> <msg>` с таймаутом 10 секунд. Скрипт берёт текст из `argv`, поэтому название задачи **не может выполниться как AppleScript**. Заголовок обрезается до 120 рун, текст до 400 (`Clip`).
- `notify.Run` — переменная, которую подменяют в тестах.
- Связка: `api.New` ставит `h.Notify = notify.System` (`api.go:80`). `app.go:140-147` назначает `Manager.Notify`: если `Setting("notify_off") == "1"`, ничего не делает, иначе показывает заголовок `"Edy · <имя папки проекта>"` и текст `"<Title>\n<сообщение>"`. Переключатель и пробное уведомление — `api.go:273-295`, маршрут `POST /api/notify/test`.
- Когда уведомляет доска:
  - `kick`: задача не началась;
  - `work`: ошибка, нужна помощь;
  - `afterDone`: готово, готово с замечаниями, принято автоматически;
  - `runEpic`: «Нужна помощь: …».
  - На Approve или Reject, сделанные человеком, уведомлений нет.

### 7.5. Память после задач

`learn(r, kind, text)` (`tasks.go:513`) работает без вызова ИИ:

- обрезает текст до `memory.MaxNote` (400 рун);
- пишет общую заметку с `Source:"task:<id>"`;
- если задачу вёл агент команды, пишет **вторую копию** с `Agent: r.Agent` в его личную память.

Когда пишется:

- **Урок** (`store.NoteLesson`) — при `needs_human`, если `lastFailure` нашла причину: первую строку с `✗` в последнем событии `hooks` или текст последнего `error` (`tasks.go:577-579`). Формат: `Задача «<title>» не удалась (<models>): <строка>`.
- **Итог** (`store.NoteTask`) — при каждом Approve, ручном или автоматическом, включая эпики (`tasks.go:750`): `«<title>»: <summary> (модель <model>)`.
- Факты (`NoteFact`) пишет сам исполнитель через инструмент `remember` (`memory.Access.Remember`). Лимит — 5 заметок на задачу. Если задачу ведёт агент команды, заметки попадают в его личную память.

`memoryapi.go`:

- `GET /api/memory?project=&agent=&q=` — фильтр по агенту (личная память), поиск `memory.Search(...,30)`; в ответе `pinned_brief` (то, что исполнитель видит сразу);
- `POST` — заметка пользователя, `Source:"user"`, не длиннее 400 рун; вид `fact|lesson|note` (по умолчанию `note`); при указании `agent` проверяется, что агент из этого проекта;
- `PUT /{id}` — закрепить или открепить;
- `DELETE /{id}?project=`.

Оркестратор получает `memory.Brief(всех заметок, последняя реплика, 2000)`, исполнитель — `Pinned` (только общие закреплённые) или `AgentBrief`.

### 7.6. Статистика моделей

- Источник — `store.ModelStats(since)` (`internal/store/agents.go:195`): попытки и успехи исполнителей (агенты журнала с `role=executor`, без `running`) плюс расходы и токены из таблицы `usage` по всем ролям.
- Попытка — это один агент журнала, то есть одна модель в цепочке Circuit Breaker. Поэтому `OnAttempt` создаёт отдельного агента на каждую модель: так статистика честная.
- Оркестратору — `statLine` за 30 дней (`projects.go:355`). Экран «Расходы» — `GET /api/stats/models?days=N` (1..365, по умолчанию 30).

## 8. Команда проекта (постоянные агенты)

`store.TeamAgent` (`internal/store/team.go:25`) содержит поля:

- `ID` (`agent_…`), `Project`, `Name`, `Emoji`;
- `Role` (инструкции);
- `Scope` (папки, маски, темы);
- `Model`, `Fallback`;
- `Skills`, `MCP` (выдаются всегда);
- `Enabled`, `Created`.

API (`teamapi.go`):

- `GET /api/team?project=` — список с подсчётом `Done` (задачи `approved` или `merged` с `Agent=id`), `Failed` (`needs_human`/`failed`/`rejected`) и `Notes` (число личных заметок). Подсчёт делает `teamStats` (`teamapi.go:33`) по доске.
- `POST /api/team` — создание или правка. Имя уникально в проекте без учёта регистра. Модель и резерв проверяются `checkModels`. Пустые элементы `Scope` выбрасываются.
- `DELETE /api/team/{id}` — удаляет агента **и его личную память** (`store.DeleteTeamAgent`, `team.go:103-112`). Задачи с этим `Agent` остаются, `roleFor` для них вернёт пустую роль.

Как агент получает задачу:

1. Оркестратор видит команду в промпте (только `Enabled`) и пишет `Агент: Имя` в плане или `"agent":"Имя"` в подзадаче.
2. `startTask` (`projects.go:505-532`):
   - `req.Agent` (id, выбран вручную) важнее, чем `PlanAgent` из плана;
   - из плана агент берётся только при `len(subtasks) < 2`;
   - у агента своя модель: `models = agentModels(a)`, то есть `[Model, Fallback]` без дубля (`teamapi.go:169`);
   - **модели, выбранные пользователем, заменяются**;
   - MCP объединяется (`union`) с `a.MCP`; скиллы объединяются с `a.Skills`, только если скиллы ограничены планом (`opts.Skills != nil`); без плана задача и так получает все скиллы;
   - `plan.Agent = a.ID`, и в `View.Agent` попадает **id**, а не имя.
3. Подзадача эпика с `agent` (`projects.go:547-551`) получает `SubPlan{Models: agentModels(a), Agent: a.ID}`. MCP и скиллы агента подзадаче **не** добавляются: она наследует MCP и скиллы эпика (`epic.go:103`).
4. При выполнении:
   - `roleFor` (`tasks.go:494-510`) добавляет в системный промпт агента:
     ```text
     Ты — «<Name>», постоянный агент команды этого проекта.
     Твоя роль:
     <Role>
     Твоя зона: <scope, …>
     Всё полезное о своей части проекта записывай через remember — это твоя память для следующих задач.
     ```
   - память: `AgentBrief(notes, agentID, goal, 2000)` — личные заметки (закреплённые и похожие на задачу, до 2/3 бюджета) и общее закреплённое;
   - `remember` пишет с `Agent=id`;
   - итоги и уроки задачи дублируются в личную память (`learn`).

## 9. Approve, finalize и git

### 9.1. `approve(id, auto)` (`tasks.go:710-755`)

1. Проверяет `state == done`.
2. Берёт `finalize` = `m.Finalize`, а если его нет, `defaultFinalize` (`tasks.go:764`): `FreeBranch(BranchName(goal))` и `agent.Approve`, то есть checkout `-b`, `add -A`, commit `Edy: <первая строка goal>\n\n<summary>\n\nМодель: <model>`.
3. **Эпик:** `applyEpic` (`epic.go:365`):
   - требует чистый проект (`CheckClean`);
   - выполняет `git merge --squash edy/epic-<id>` в рабочую папку без коммита;
   - при конфликте делает `git reset -q --hard HEAD` и возвращает ошибку «результат эпика не накладывается… (его меняли после начала эпика)».
   - `defer cleanupEpic` удалит worktree и ветки эпика **в любом случае** после применения. См. «грабли».
4. `agent.HasChanges(project)` (`internal/agent/task.go:523`):
   - если изменений нет, итог «изменений нет — коммит не нужен», finalize не вызывается (защита от пустого коммита или ошибки «nothing to commit»);
   - в папке без git `HasChanges` всегда `true`.
5. Если у задачи есть `IssueRef`, к summary добавляется `\n\nCloses <ref>`, чтобы хостинг закрыл issue коммитом или PR.
6. `update`: `approved`, `Branch`, `PRURL`, `Note`. Событие `approved`, итог в память. Если не авто, запускается `go kick`.

### 9.2. `api.Finalizer` (`gitapi.go:290-315`) — продакшен-finalize

- Читает `ProjectSettings` и аккаунт (`AccountID`, если не 0).
- `title` = первая строка goal, имя ветки = `agent.FreeBranch(ctx, project, agent.BranchName(goal, time.Now()))`.
- Вызывает `gitops.Finalize(ctx, project, ps, acc, branch, title, summary+"\n\nМодель: "+model)`.
- `Outcome.Branch` заполняется только если был коммит.

`agent.BranchName` (`internal/agent/task.go:510`) строит `edy/<slug>-MMDD-HHMM`: slug — транслит первой строки goal в нижнем регистре, `[^a-z0-9]+` заменяется на `-`, длина до 40, пустой slug становится `task`.

### 9.3. Настройки проекта (`store.ProjectSettings`, `internal/store/git.go:111`)

Хранятся в `settings` под ключом `project:<path>`. По умолчанию (`DefaultProjectSettings`): `Commit=branch`, `Push=off`, `Prefix="Edy: "`.

| Поле | Значения | Эффект |
|---|---|---|
| `Commit` | `branch` (новая ветка `edy/…`), `direct` (коммит в текущую ветку), `none` (без коммита) | `gitops.Finalize` |
| `Push` | `off`, `push`, `pr` | `pr` допустим только при `Commit=branch` и с аккаунтом (`gitapi.go:211-218`) |
| `AccountID` | id `GitAccount` | Токен для push и PR |
| `AuthorName`, `AuthorEmail` | оба или ни одного | `--author=` в коммите (коммиттер остаётся пользователем) |
| `Prefix` | строка | Префикс заголовка коммита и PR |
| `AutoApprove` | bool | см. §7.1 |
| `ReviewModel` | `""`, `off`, `провайдер/модель` | см. §7.3 |
| `MaxParallel` | 0..6 (0 значит 2) | сколько подзадач эпика одновременно; также подставляется в промпт Оркестратора |

Сохраняет `PUT /api/git/settings` (`gitSettings`, `gitapi.go:186-245`) после всех проверок. `gitClone` с аккаунтом сразу пишет для нового проекта настройки по умолчанию с этим `AccountID`.

### 9.4. `gitops.Finalize` (`gitops.go:113-178`)

```
не git-репозиторий ──► «Папка без git: изменения оставлены в ней…» (ok, без коммита)
Commit=none        ──► «Коммит отключён…» (ok)
base = текущая ветка
Commit=branch      ──► check-ref-format; checkout -q -b newBranch
git add -A; git commit -q -m "<Prefix><title>\n\n<body>" [--author=…]
Push=off/""        ──► «Коммит в ветке X (основная ветка base не изменилась)»
Push               ──► git -c http.extraHeader=Authorization: Basic … push -u origin <branch>
                       ошибка push НЕ ошибка Finalize: дописывается в Note
Push=pr && branch  ──► acc==nil → «PR не создан: не выбран аккаунт»
                       CreatePR(acc, origin-url, base, branch, Prefix+title, body)
                       ошибка PR → в Note, не в err
```

Обратите внимание:

- при `Commit=branch` проект **остаётся на новой ветке** (checkout);
- `authArgs` (`gitops.go:46`) передаёт токен заголовком **только на время команды**, не в URL и не в `.git/config`. Имя пользователя по умолчанию: GitHub — `x-access-token`, GitLab — `oauth2`, иначе `edy`;
- все git-команды идут с `GIT_TERMINAL_PROMPT=0`.

`CreatePR` (`pr.go:20`):

| Kind | Endpoint | Авторизация | Ссылка |
|---|---|---|---|
| GitHub | `https://api.github.com/repos/<repo>/pulls` или `<host>/api/v3/…` (Enterprise, если host не `https://github.com`) | `Bearer` | `html_url` |
| Gitea | `<host>/api/v1/repos/<repo>/pulls` | `token …` | `html_url` |
| GitLab | `<host>/api/v4/projects/<url-escaped repo>/merge_requests` (`source_branch`/`target_branch`/`description`) | `PRIVATE-TOKEN` | `web_url` |

`repo` берётся из `RepoPath(remote)`: поддерживаются `https://host/owner/repo.git`, `git@host:owner/repo.git`, `file://`.

Прочие функции gitops:

- `GetInfo` — для вкладки Git: ветка, origin без логина и пароля (`stripCredentials`), `status --short`, последние 8 коммитов;
- `Push`/`Pull` (`--ff-only`) — для кнопок вкладки Git; `gitRemoteAction` запрещает их, пока в проекте идёт задача;
- `Clone` — в `<home>/repos/<name>[-N]`, проект добавляется в начало списка (не больше 10 проектов).

### 9.5. Импорт issue и шаблоны

`POST /api/board/issue` (`importIssue`, `projects.go:604-657`):

1. `gitops.ParseIssueURL` (`issue.go:43`) принимает только http(s):
   - `…/-/issues/N` — GitLab (группы любой вложенности);
   - `/owner/repo/issues/N` — `github.com` даёт GitHub, другой хост — Gitea, **если нет аккаунта с этим хостом** (тогда берётся Kind аккаунта, например GitHub Enterprise);
   - ссылка на PR (`/pull/1`) отвергается.
2. Ищется аккаунт с тем же хостом. `FetchIssue` (`issue.go:76`) отправляет токен, **только если хост аккаунта совпадает с хостом issue**. Ответы 404/401 дают понятную ошибку про приватный репозиторий. У GitLab используются поля `iid`, `description`, `web_url`. Метки разбираются и строками, и объектами `{name}`.
3. Карточка в пуле:
   - заголовок `#N <title>`;
   - Request: `Issue: <url>\nМетки: …\n\n<title>\n\n<body>`, тело обрезано до 6000 рун;
   - `IssueURL`;
   - `IssueRef`: `owner/repo#N` для GitHub, `#N` для остальных.
   - Через `IssueRef` Approve добавит `Closes …`.

Шаблоны (`projects.go:659-731`): 8 встроенных (`builtinTemplates`) и свои. Свои хранятся в `settings["task_templates"]`: JSON-массив, до 50 штук, каждый до 1000 рун, без дублей. `{файл}` — плейсхолдер, который заполняет UI; сервер его не обрабатывает.

## 10. Эпики (`epic.go`, `worktree.go`)

### 10.1. Создание

`startTask` с `len(subtasks) >= 2` (`projects.go:542-561`) строит `[]tasks.SubPlan`:

- подзадача с известным агентом команды получает его модели и `Agent=id`;
- иначе `checkModels([st.Model])`, и неизвестная модель даёт 400 на весь запрос; если у задачи есть резерв `models[1]` и он отличается от модели подзадачи, он добавляется вторым в цепочку.

`EnqueueEpic(id, d, p, subs)` (`epic.go:59-121`):

1. Проверки: подзадач 2..6 (`maxSubtasks`), у каждой `Goal` и `Models`, `After` указывает только на **меньшие** номера (циклов быть не может). Проект должен быть git (`isGitRepo`).
2. `p.Models` пуст → берутся модели первой подзадачи.
3. Если `id` задан, сначала `Unsplit(id)`: старое деление удаляется.
4. `enqueue(..., start=false)`: эпик в `queued`, **без kick**, потому что подзадач ещё нет.
5. Под `m.mu`:
   - создаются подзадачи: `Kind=sub`, `Parent=epicID`, `Step=i+1`, `After`, `State=queued`, MCP, скиллы и `AllSkills` от эпика, `Position = now+i`;
   - `Goal` подзадачи:
     ```text
     Общая задача:
     <goal эпика>

     Твоя часть — подзадача i из N: <title>
     <goal подзадачи>

     Все части эпика:
     1. …
     2. …

     Остальные части делают другие агенты параллельно, в своих копиях проекта. Делай только свою часть и не трогай файлы, которые относятся к другим частям, без необходимости.
     ```
   - эпику ставится `Kind=epic`, пишется событие `subtask` «Оркестратор разбил задачу на N подзадач».
6. `go kick`.

### 10.2. Выполнение (`runEpic`, `epic.go:166-280`)

```
 основной проект (не меняется до Approve)
 │  HEAD = base
 │
 ├── .edy/worktrees/<epicID>/main   ← integ worktree, ветка edy/epic-<hex>  (от base)
 │        ▲  merge --no-ff подзадачи 1   (под integMu)
 │        ▲  merge --no-ff подзадачи 2
 │        ▲  …
 ├── .edy/worktrees/<epicID>/1      ← ветка edy/epic-<hex>-1 от текущего HEAD integ
 ├── .edy/worktrees/<epicID>/2      ← ветка edy/epic-<hex>-2 от текущего HEAD integ
 └── .edy/worktrees/<epicID>/3      ← (after:[2]) стартует только после слияния 2,
                                       поэтому видит изменения 1(если уже слита) и 2
 итог: hooks на integ → diff/patch от base → state=done → afterDone (ревью/авто)
 Approve: git merge --squash edy/epic-<hex> в основной папке → Finalize (как обычная задача)
          → cleanupEpic (worktree remove, prune, branch -D всех веток эпика)
```

Шаги:

1. `base = git rev-parse HEAD` основного проекта.
2. `branch = "edy/epic-" + id без "task_"`. Перед созданием вызывается `removeEpicWorktrees` на случай остатков прошлого запуска. Затем `addWorktree(integ, branch, base)`, и в карточку пишутся `EpicBase` и `EpicBranch`.
3. Цикл планировщика (в одной горутине):
   - пока нет провала и отмены, стартует каждая неначатая подзадача, у которой все `After` уже **слиты** (`merged[a]`), пока `running < par` (`maxParallel`: `MaxParallel(project)`, если больше 0, иначе 2);
   - каждая подзадача работает в своей горутине (`m.running.Add(1)`) и шлёт `subResult` в небуферизованный канал;
   - цикл ждёт результат; при провале ставится `failed=true`, новые подзадачи не стартуют, но уже идущие **дорабатывают до конца**.
4. `runSub` (`epic.go:283-337`):
   - берёт HEAD integ под `integMu`;
   - `addWorktree(<epicDir>/<step>, <branch>-<step>, head)`;
   - `defer git worktree remove --force` (сама ветка остаётся до `cleanupEpic`);
   - подзадача получает `running` и `SubBranch`;
   - `execute` в worktree: агент делает свой Shadow Git **внутри worktree** (`<wt>/.edy/shadow.git`) и прогоняет хуки там;
   - итоги: отмена → `cancelled`; err → `failed`; не `StatusDone` → `needs_human` «ни одна модель не прошла проверки»;
   - `commitAll` (`add -A`, `commit --no-verify`, без gpg, автор `Edy <edy@localhost>`; если изменений нет, коммита нет, это не ошибка);
   - под `integMu`: `git merge --no-ff --no-edit -m "Эпик: подзадача N «…»" <branch>`, при ошибке `merge --abort` и `needs_human` «конфликт при слиянии с другими подзадачами…»;
   - успех → `merged` с summary, model и diff; событие `approved` у подзадачи и `info` у эпика.
5. После цикла:
   - отмена → эпик `cancelled`, `cleanupEpic`;
   - провал или не все слиты → `fail()`: эпик `needs_human`, `cleanupEpic`, уведомление.
6. Общие проверки: `agent.DetectHooks(integ)` и `RunHooks`. Провал даёт `fail` «подзадачи слиты, но общие проверки не прошли…».
7. `diff --stat base` даёт `Diff`, `diff -U3 base` даёт `Patch` (до 400 КБ). `Summary` — строки `N. Title — summary` по подзадачам, `Model` — модели эпика через запятую. Состояние `done`, затем `afterDone(final, "")`.
8. `defer`: удалить `active`, затем `kick`.

### 10.3. Решения по эпику

- **Approve:** см. §9.1. Один squash-коммит на весь эпик по настройкам проекта.
- **Reject** (`tasks.go:783-786`): основная папка не менялась, поэтому достаточно `cleanupEpic`. Подзадачи остаются `merged` в истории.
- **RevertFile** для эпика запрещён (`tasks.go:843-845`).
- **Cancel:** `Cancel(epicID)` отменяет контекст, и все `runSub` получают отмену. `Cancel(subID)` для выполняющейся подзадачи вернёт ошибку «задача уже не выполняется», потому что `active[project].id` — это эпик.
- **Повторный запуск** (кнопка после `needs_human`, `cancelled` и т.п.): `enqueue` видит `Kind=epic` и вызывает `resetEpic` (`epic.go:379`). Все подзадачи снова `queued` с очищенными `Error/Summary/Diff/SubBranch`. **Прогон начинается заново с нуля**: слитые раньше подзадачи тоже переделываются, потому что ветка эпика удаляется в `fail()` и `cleanupEpic`.
- **Delete эпика:** `cleanupEpic`, затем удаление всех подзадач и карточки.

### 10.4. `Unsplit` (`epic.go:41-56`)

- Убирает деление: `cleanupEpic`, удаление подзадач, `Kind/EpicBranch/EpicBase = ""`.
- Не работает для `running`/`done`/`queued` (ошибка). Для не-эпика ничего не делает и возвращает `nil`.
- Вызывается:
  - из `EnqueueEpic(id≠"")` — новое деление вместо старого;
  - из `startTask`, когда приходит **новый план без деления** для задачи из пула (`projects.go:535-541`).
- Без этого при повторном планировании на доске накапливались дубликаты подзадач, а «обычная» задача продолжала исполняться как эпик со старыми подзадачами.

### 10.5. Очистка

`cleanupEpic` (`epic.go:355`) → `removeEpicWorktrees(project, epicID, [EpicBranch, SubBranch…])` (`worktree.go:60`):

- `git worktree remove --force` для каждой подпапки `.edy/worktrees/<epicID>/*`;
- `os.RemoveAll` папки;
- `git worktree prune`;
- `git branch -D` для каждой непустой ветки.
- Ошибки игнорируются: функция «максимально чистит».

Где вызывается:

- `fail()` и отмена в `runEpic`;
- `Reject`, `Approve` (через defer), `Delete`, `Unsplit`;
- `Recover` (для эпика в `running`).

  - только `data:image/{png,jpeg,gif,webp};base64,…`, SVG отвергается;
  - до 5 МБ на файл (`maxAttachment`), до 8 на задачу (`maxAttachments`);
  - имя очищается `safeName` (буквы, цифры, `._-`), до 40 рун; итоговое имя `<n>-<base><ext>`;
  - файл пишется в `<AttachDir>/<taskID>/` с правами `0600`, папка `0700`;
  - `AttachDir = <home>/attachments` (`app.go:122`), это не папка проекта.
- `attachDir` проверяет, что id начинается с `task_` и не содержит `/ \ .`. `AttachmentPath` отдаёт файл, только если он есть в списке `Attachments` карточки: защита от обхода пути.
- `images(r)` отдаёт модели не больше 4 картинок (`maxSentImages`). Дальше `agent.Task` решает через `CanSee`: модель без зрения получает предупреждение в ленте («не видит картинки»).
- `Delete` карточки удаляет её папку вложений.
- API: `addAttachment` читает тело с лимитом 8 МБ; `getAttachment` отдаёт с `Cache-Control: private, max-age=3600`.

## 13. Старт, восстановление и конкурентность

### 13.1. Запуск (`internal/app/app.go:115-164`)

`NewManager(OmniRoute{Client:"agent"}, store)`, затем назначаются `Journal`, `SkillsHome=home`, `Notes`, `Semantic`, `Team`, `AttachDir`, `CanSee`, `MCP=h.MCPBridge()`, `Review` (OmniRoute `Client:"reviewer"`), `Notify`, `MaxParallel`, `AutoApprove`, `Finalize=api.Finalizer(st)`.
После этого `st.InterruptRunningAgents()` (журнал) и **`h.Tasks.Recover()`** вызываются **до** того, как HTTP-сервер начнёт принимать запросы.

### 13.2. `Recover` (`tasks.go:928-960`)

- Все карточки в `running` становятся `failed` с текстом «прервана: Edy закрыли во время работы».
- Обычная задача с `Baseline` откатывается (`agent.Reject`), к тексту добавляется «, проект откачен к началу задачи».
- Эпик и подзадача: основная папка не менялась; для эпика вызывается `cleanupEpic`.
- Затем `kick` по **каждому** проекту, где есть карточки: очереди продолжаются. Задача в `done`, ждущая решения, по-прежнему блокирует свою очередь.

### 13.3. Мьютексы и горутины

| Примитив | Что защищает |
|---|---|
| `Manager.mu` (`tasks.go:188`) | `active` и все `update` (load, изменение, save). Под ним выполняются `kick` целиком (включая `BoardTasks`, `CheckClean`, `skills.Load`) и создание подзадач в `EnqueueEpic`. |
| `Manager.running` (`sync.WaitGroup`) | Каждая `work`, `runEpic` и каждая подзадача `runSub`. `Wait()` (`tasks.go:963`) — для тестов и выключения. `Add(1)` в `runEpic` вызывается, пока счётчик уже больше нуля (держит сам `runEpic`), так что это корректно. |
| `agentsMu` в `execute` | `ru.agentID`, `ru.pending`. |
| `integMu` в `runEpic` | Все git-операции в integ worktree (`rev-parse HEAD`, `merge`/`merge --abort`). Без него параллельные слияния портили бы индекс. |

Правила, которые нельзя нарушать:

- **Не вызывайте `update`, `kick` или `Running` изнутри `fn` у `update`**: `sync.Mutex` не реентерабелен, будет дедлок. Внутри `update` можно только `load`/`save` (они без блокировки) и `agent.Reject` (как в `Recover`).
- `kick` держит `m.mu` во время git-команд (`CheckClean`). Это осознанное упрощение. Пока оно идёт, все `update` ждут. Не добавляйте в `kick` долгих операций (сеть, LLM).
- Событие и уведомление при неудачном старте `kick` отправляет через `go` именно потому, что `notify` может быть медленным (`osascript`).
- Горутина задачи работает со **своей копией** `record`. Всё, что пишется в базу, должно идти через `update` (перечитать, изменить, сохранить), а не через `save` старой копии. Исключение — `kick` и `EnqueueEpic`: они под `m.mu` сразу после `load`.
- `Approve` и `Reject` **не** держат `m.mu` между проверкой `state == done` и `update`. Два одновременных Approve (двойной клик, автопринятие и человек одновременно) теоретически оба вызовут finalize. В UI это закрыто блокировкой кнопки, на сервере защиты нет. См. TODO.
- Тесты гоняйте с `-race` (см. §15). Колбэки `OnEvent`, `OnAttempt` и `OnAttemptEnd` приходят из горутин агента и MCP-моста.

### 13.4. Почему `context.WithoutCancel` в Shadow Git

`internal/agent/shadow.go:31-36`: каждая git-команда теневого репозитория выполняется с `context.WithTimeout(context.WithoutCancel(ctx), 5*time.Minute)`.
Остановка задачи (Cancel) отменяет ctx. Если бы git-процесс снимка убивался на полпути, оставались бы `index.lock` и неполные объекты. Тогда откат (`Reject` к Baseline) падал бы, и проект оставался бы в промежуточном состоянии.
**Не передавайте отменяемый ctx в git снимков напрямую.**

## 15. Тесты

Запуск:

```bash
# только эта область
go test ./internal/orchestrator/ ./internal/tasks/ ./internal/review/ ./internal/notify/ ./internal/gitops/ ./internal/api/

# с детектором гонок (обязательно после правок в tasks/epic — там много горутин)
go test -race ./internal/tasks/ ./internal/api/

# один тест подробно
go test -race -run TestEpicConflictAndDependencies -v ./internal/tasks/
```

Нужен установленный `git`, без него тесты `tasks` и `gitops` пропускаются (`t.Skip`). Тесты сами задают `GIT_AUTHOR_*`, `GIT_COMMITTER_*` и `GIT_CONFIG_GLOBAL=/dev/null`, поэтому глобальный конфиг (подпись коммитов и т.п.) им не мешает.
На момент написания все пакеты области проходят с `-race`.

Тестовая инфраструктура `tasks`:

- `project(t)` — временный git-репозиторий с `go.mod`, «сломанным» `calc.go` (`Add` вычитает) и `calc_test.go`. Хук `go test` настоящий.
- `fixer` — фейковый LLM: первый шаг `replace_in_file a - b → a + b`, затем `finish`. Канал `gate` позволяет держать задачу в `running`.
- `newMgr` — настоящий `store` SQLite во временной папке, `t.Cleanup(m.Wait)`.
- `wait` опрашивает состояние до 2 минут.
- `team` (epic_test) — фейковый LLM для подзадач: по тексту «подзадача N из» пишет `sub.go`/`mul.go`/`sq.go`, задерживается на 300 мс и меряет одновременность (`maxPar`) и порядок старта (`order`). С `conflict: true` обе подзадачи правят одну строку.

## 16. Грабли, ограничения, история исправлений

### 16.1. Исправленные баги — не вернуть обратно

1. **Коллизия имён веток.** Две задачи с одинаковой первой строкой, принятые в одну минуту, давали одинаковое `edy/<slug>-MMDD-HHMM`, и `checkout -b` падал. Исправлено через `agent.FreeBranch` (`internal/agent/task.go:533`): добавляет `-2`, `-3`, … (до 99). Используется в `defaultFinalize` (`tasks.go:766`) и `api.Finalizer` (`gitapi.go:305`). **Любой новый путь создания ветки должен идти через `FreeBranch`.**
2. **Approve задачи без изменений.** Если агент ничего не поменял (всё уже было сделано), `git commit` падал «nothing to commit», и Approve был невозможен, а очередь стояла навсегда. Теперь `approve` сначала спрашивает `agent.HasChanges` (`tasks.go:729-741`). Не убирайте эту проверку и не переносите её после `applyEpic`.
3. **Порча Shadow Git при Cancel.** Отменённый ctx убивал git посреди снимка, оставляя `index.lock`, и откат не работал. Исправлено через `context.WithoutCancel` в `Shadow.git` (`internal/agent/shadow.go:35`), а также `context.Background()` для отката в `work` (`tasks.go:556`) и для `Patch`.
4. **`.edy/` делала проект «грязным».** Скиллы проекта в `.edy/skills`, снимки и worktree лежат в проекте, и `CheckClean` видел их как незакоммиченные изменения, после чего очередь падала. Исправлено через `excludeEdyDir` (`internal/agent/task.go:488`): добавляет `.edy/` в `.git/info/exclude`, не трогая `.gitignore` проекта. Вызывается в `CheckClean`, `Task.Run`, `OpenShadow`. Если добавляете новые служебные файлы, кладите их под `.edy/`.
5. **Дубликаты подзадач при повторном планировании.** Повторный план для той же задачи создавал ещё один набор подзадач поверх старого. Исправлено через `Unsplit` в начале `EnqueueEpic` (`epic.go:80-84`) и в `startTask` для плана без деления (`projects.go:535-541`).

### 16.2. Известные ограничения и подводные камни

- **Одна задача на проект.** Параллельность есть только внутри эпика. Результат в `done` блокирует очередь, пока по нему не принято решение (это задумано). При включённом `AutoApprove` очередь идёт сама.
- **`kick` при грязном проекте** переводит в `failed` только первую задачу очереди. Остальные стоят до следующего события (Enqueue, Approve, Reject, перезапуск). Само это не «самоисцеляется».
- **Неудачный finalize эпика.** `applyEpic` уже сделал `merge --squash` в рабочую папку, затем `finalize` вернул ошибку (например, неверное имя ветки или ошибка commit). `defer cleanupEpic` **всё равно удаляет ветку эпика**, а рабочая папка остаётся грязной, задача остаётся `done`. Повторный Approve падает на `CheckClean`, Reject только чистит worktree (которых уже нет), а squash-изменения так и остаются в папке. Ошибки push и PR сюда не относятся: они не считаются ошибкой `Finalize`. **Кандидат на исправление:** вызывать `cleanupEpic` только при успехе, а при ошибке делать `reset --hard`.
- **Двойной Approve** — гонка, см. §13.3. Защита пока только в UI.
- **Approve при `Commit=branch` оставляет проект на новой ветке.** Следующая задача начнётся от неё. Это осознанно: следующая задача видит предыдущий результат. Но пользователи иногда ожидают возврата на main.
- **Эпик требует чистого проекта на Approve** и неизменённой базы. Если пользователь закоммитил что-то в основной ветке во время эпика, squash может не наложиться. Тогда эпик остаётся в `done`, и остаётся только Reject.
- **Повторный запуск эпика переделывает все подзадачи**, в том числе уже слитые (`resetEpic`). Инкрементального продолжения нет.
- **Подзадачу нельзя остановить отдельно**, только весь эпик (`Cancel` смотрит на `active[project].id`).
- **При провале одной подзадачи** остальные уже начатые доделываются до конца: тратятся токены. Новые не стартуют.
- **Подзадача с агентом команды** не получает личные MCP и скиллы агента (наследует эпиковые), а её итоги и уроки не пишутся в личную память агента: `learn` вызывается только из `work` и `approve` эпика. Роль и выжимку памяти агента она получает.
- **Статистика команды** (`teamStats`) засчитывает подзадачу в `merged` как успех, даже если эпик потом отклонили.
- **`startTask` не проверяет MCP-возможность исполнителя** при разборе `MCP:` из плана. Это не опасно: `agent.Task` сам не выдаёт `Extra` моделям без MCP. Но список MCP в карточке может вводить в заблуждение.
- **`orchestrate` кладёт в `Memory` личные заметки агентов**: `memory.Brief` по всем заметкам без фильтра `Agent == ""`. `Pinned` для исполнителя их отфильтровывает, а для Оркестратора — нет.
- **Имена MCP-серверов и скиллов с пробелами** не разбираются из строк плана: разделитель включает пробел.
- **`ErrBusy` объявлен, но не используется** (`tasks.go:78`).
- **`List` делает N+1 чтений** (`BoardTasks`, затем `load` каждой карточки). На больших досках это медленно. `children` и `Pending` тоже читают всю доску проекта.
- **Ревьюер видит только первые 60 КБ** patch, а сам patch хранится до 400 КБ. Большие изменения ревьюятся частично (в тексте есть пометка об этом).
- **Обработчики по id карточки** (`getTask`, `taskAction`, `deleteTask`, вложения) не проверяют `knownProject`. API доступен только по токену на 127.0.0.1, но имейте это в виду.
- **Worktree и `info/exclude`.** `excludeEdyDir` внутри worktree пишет в `.git/worktrees/<n>/info/exclude`. Git этот файл не читает (exclude общий для всех worktree), но `.edy/` уже исключена в основном репозитории при `CheckClean` в `kick`, поэтому всё работает. Если поменяете порядок проверок, проверьте, что `.edy/shadow.git` внутри worktree не попадает в `commitAll` подзадачи.
- **Коммиты подзадач** делает Edy с автором `Edy <edy@localhost>`, без подписи и `--no-verify`. В итоговый коммит эпика они не попадают (squash), автор итогового коммита определяется настройками проекта.
